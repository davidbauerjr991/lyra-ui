# TabList / overflowMenu saga (archived)

### TabList gains a native `overflowMenu` responsive-collapse behavior (`tabs.tsx`)
- **Request**, from a two-panel screenshot of a "Sarah C." agent record's Overview/Details/Tickets/Accounts/Interactions/Directory/Tasks/Scheduled Callbacks/History tab bar at full width vs. below 991px: "add a responsiveness to the tab component in lyra-ui... make this behavior native to all tabs: When a container goes below 991px, display 2 tabs full width: 1) the active tab 2) the amount of available tabs. When a new tab is selected, display that tab in the active area and move the current active tab to the position in the list if the tabs were above 991px."
- **New `TabList` props**: `overflowMenu?: boolean` (opt-in, default `false`) and `overflowMoreLabel?: (count: number) => string` (defaults to `` `${count} More` ``). When set, `TabList` renders two rows inside a new `.lyra-tab-overflow-wrap` container-query boundary: the real `role="tablist"` row (tagged `.lyra-tab-overflow-full`, hidden below 991px — stays in the DOM so its buttons can still be `.click()`ed programmatically) and a collapsed two-slot row (tagged `.lyra-tab-overflow-collapsed`, the reverse — hidden above 991px). The collapsed row is a cloned copy of whichever `Tab` currently has `active` set, plus a "{n} More" dropdown button (built on the real `Menu` primitive, portal-positioned exactly like `KebabMenuButton`'s own trigger) listing every other tab in its original `children` order.
- **No separate reordering logic needed**: clicking a dropdown entry calls `.click()` on the corresponding hidden real tab button (same "trigger the actual DOM click, don't hand-call `onClick` props" pattern this file's own arrow-key navigation already uses) rather than tracking any list order itself. Because the "active tab" and "other tabs" list are both re-derived fresh from each `Tab`'s own `active` prop on every render, the tab that was active a moment ago automatically reappears in the dropdown at its original position — satisfying the "move the current active tab to the position in the list" part of the request with no extra state.
- **Deliberately opt-in, not forced on every `TabList`**: `ChannelTab` (`channel-row.tsx`) already implements a different collapse strategy — shedding each tab's own text, never moving tabs into a menu — at much narrower, unrelated breakpoints (480px/320px) via its own `.lyra-channel-tab-list-wrap`. Making this new behavior unconditional for every `TabList` would fire at 991px before that narrower, purpose-built behavior ever got a chance to run, regressing every existing `ChannelTab` bar. Any new tab bar that wants this pattern (record detail panels, settings pages, etc.) opts in with `overflowMenu`.
- New CSS added to both `lyra-tokens.css` and `storybook.css` (kept in sync, per convention): `.lyra-tab-overflow-wrap` (`container-type: inline-size`), `.lyra-tab-overflow-collapsed` (default `display: none`), and the `@container (max-width: 991px)` pair that flips which of the two rows is visible.
- New story: `Tabs.stories.tsx`'s `OverflowMenu` ("Overflow Menu (Responsive)") — a `resize-x` dashed box (same demo pattern as `ChannelRow.stories.tsx`'s `ChannelTabResponsive`) around the exact 9-tab set from the reference screenshot, so the collapse can be seen live by dragging its edge.
- Verified live via a Storybook static build + Claude-in-Chrome: full width shows all 9 tabs; shrinking below 991px collapses to "Overview" + "8 More ⌄" pill (pixel-matching the reference screenshot); opening the dropdown lists the other 8 in order; selecting "Tickets" swaps it into the active slot; reopening the dropdown confirms "Overview" reappears first, in its original position, with the rest of the order unchanged.
- Verified with `tsc --noEmit`/Storybook build (lyra-ui — same 3 pre-existing, unrelated errors as above, untouched by this change) and `npx vite build` in both `agent-next-gen-v1` and `lyra-ux-templates` (clean — neither app opts into `overflowMenu` yet, so this is a purely additive, currently-unused capability there, same posture as the `initialInteraction`/`sidePanelToggleLabel` entry above).

### Follow-up: real bug — the "Desk" tab bar showed BOTH rows at once in `agent-next-gen-v1`, not the collapsed pair
- **Report**: a screenshot of the real running `agent-next-gen-v1` app's "Desk" tab bar (see the previous entry) at a narrow width showing the full Dashboard/Customers/Accounts/Tickets/Interactions/WEM row *and* the collapsed "Accounts / 5 More" row stacked on top of each other, instead of only one.
- **Root cause**: `.lyra-tab-overflow-full`/`.lyra-tab-overflow-collapsed` were bare single-class selectors, and the element they toggle (`TabList`'s own `role="tablist"` row) *also* carries Tailwind's own `.flex` utility class from `TabList`'s base styling (`cn("flex border-b ...", ..., overflowMenu && "lyra-tab-overflow-full", ...)`). `.lyra-tab-overflow-full { display: none }` and `.flex { display: flex }` are both single-class selectors — identical specificity — so when two rules tie on specificity, plain CSS cascade order (whichever rule appears later in the final stylesheet) decides, and that ordering is bundler behavior, not something this component controls. Confirmed by inspecting both real built CSS files byte-for-byte: in the Storybook build, `.lyra-tab-overflow-full`'s rule happened to land after `.flex`'s, so it won and the story looked correct; in `agent-next-gen-v1`'s Vite build, Tailwind's utilities landed *after* `lyra-tokens.css`, so `.flex` won instead and the "hide the full row" rule was silently overridden — while `.lyra-tab-overflow-collapsed`'s own show-rule (no competing utility on that element) still applied normally, so both rows ended up visible together. This is exactly the "identical behavior implemented once but two different builds happen to resolve a same-specificity tie in opposite directions" failure mode — the Storybook check in the original entry passing was not proof the CSS was actually correct, just that Storybook's particular bundle order happened to mask the bug.
- **Fix**: scoped both selectors with the `.lyra-tab-overflow-wrap` ancestor (`.lyra-tab-overflow-wrap .lyra-tab-overflow-full` / `.lyra-tab-overflow-wrap .lyra-tab-overflow-collapsed`) in both `lyra-tokens.css` and `storybook.css`, raising specificity to two classes — this beats a single-class utility unconditionally, regardless of which stylesheet loads first in any given bundler's output. Confirmed via byte-offset inspection of the rebuilt `agent-next-gen-v1` CSS that the ancestor-scoped rule is present and no longer tied with `.flex`.
- **Takeaway for any future container-query class placed on an element that might also carry a plain Tailwind display/layout utility** (`flex`, `grid`, `block`, `hidden`, etc.): always scope the container-query selector with its wrapper ancestor rather than a bare single class, even though every other existing container-query class in this file (`.lyra-container-grid`, `.lyra-metric-row`, `.lyra-channel-tab-list-wrap`'s own targets) happens not to have this specific collision, since none of *their* toggle targets also carry a same-named Tailwind utility on the same element — checked and confirmed clean, this was a `TabList`-specific risk, not a systemic one.
- Verified: rebuilt `agent-next-gen-v1`'s `vite build` and confirmed the ancestor-scoped selector is present in the output CSS at the correct specificity. (Live browser confirmation against the actual running app wasn't reachable from this session's sandbox — same `localhost` port-isolation limitation noted earlier for port 6007 — so this fix is verified by direct CSS specificity reasoning plus inspecting the real built output, not a live click-through.)

### `TabList`'s `overflowMenu` needed a content-aware mode for panel-width contexts, not just a lower fixed threshold
`overflowMenu`'s responsive collapse was hardcoded to a single ≤991px `@container` threshold (`.lyra-tab-overflow-wrap`, tabs.tsx/lyra-tokens.css) — tuned for a wide record-detail page's own tab bar. The Settings interior panel's tabs (`FormDetailPage.tsx`, Design/General/Activity/History) were built with plain `TabList` and no `overflowMenu` at all, reasoning that turning it on would be pointless: `InteriorPanel` is fixed/resizable between 200–425px (later 350–425px), always under 991px, so it'd permanently show the collapsed "active + N more" state with no visible response as the panel resized. But leaving `overflowMenu` off entirely meant the tab row had *no* responsive behavior at all — at the panel's narrower widths, tabs just clipped ("History" cut off at the edge), confirmed by screenshot.

First fix attempt: an `overflowBreakpoint?: "wide" | "compact"` prop where `"compact"` used a *different but still fixed* `@container` threshold (≤400px, a separate `.lyra-tab-overflow-wrap-compact` class chosen to sit inside `InteriorPanel`'s ~350–425px range). This visibly toggled as the panel resized, but the user rejected it: they wanted all tabs to stay visible for as long as they actually fit, only collapsing once they'd genuinely start clipping — not at a guessed pixel number that has no real relationship to whether these specific tab labels fit at that width.

Final fix: `"compact"` was reimplemented as content-aware measurement instead of a fixed threshold. `TabList` renders a hidden, unconstrained clone of the tab row (`aria-hidden`, `inert`, absolutely positioned, `whiteSpace: nowrap`, no wrapping ancestor) purely to read its natural `scrollWidth` — the true space all the tabs need with nothing squeezing them — and compares that via `ResizeObserver` to the visible wrapper's actual `clientWidth`, collapsing only when the real row would clip. This works regardless of the panel's width *or* the tab labels' lengths, so it needed no CSS `@container` rule at all (the `.lyra-tab-overflow-wrap-compact` class and its lyra-tokens.css/storybook.css rules were removed once this landed). General lesson: when a "responsive" behavior needs to react to whether content *actually* fits rather than a specific known reference width, a fixed `@container`/`@media` breakpoint is the wrong tool even if you pick a "better" number for it — reach for a measured (hidden-clone + `ResizeObserver`) comparison instead.

### `TabList`'s "compact" measurement clone needs `overflow-x-hidden` on its own wrapper
The hidden clone used to measure a `compact`-mode `TabList`'s true unconstrained width (see the entry above on `overflowMenu`) is deliberately wider than its wrapper — that's the point, it's how the real width gets measured — but `visibility: hidden` only stops it from being *painted*, not from still occupying layout space. Left unclipped, an ancestor with its own scrollable overflow (e.g. `PanelContent`, `overflow-y-auto` — which per the CSS overflow spec implicitly forces the *other* axis to `auto` too instead of leaving it `visible`) picked up the clone's extra width and showed an unwanted horizontal scrollbar under the actually-visible tabs. Fixed by adding `overflow-x-hidden` to the compact wrapper div itself (tabs.tsx) so the clone's overflow is contained right where it's produced, rather than bubbling up into an ancestor's scroll area. General lesson: an off-screen/hidden element built purely for measurement can still affect a scrollable ancestor's layout unless its own container explicitly clips it — `visibility: hidden` and `display: none` are not equivalent here (the former keeps taking up space; only the latter removes it from layout entirely, which isn't an option when the whole point is to keep measuring it).

### Every `TabList` needs `overflowMenu` — this has been missed more than once
`overflowMenu` (tabs.tsx) is what makes a `TabList` collapse to "active tab + N More" instead of letting its tabs clip or wrap once they no longer fit the row's own available width — it's a real prop that already exists, not something that needs building. It defaults to `false` specifically so components with their own different, narrower-purpose collapse strategy (`ChannelTab`, a much narrower breakpoint that sheds tab text instead of moving tabs into a menu) don't have this fire underneath them unasked — but that opt-in default has repeatedly been read as "responsive collapse is optional for a new tab bar," which is backwards. Concrete incident: Outbound-Campaigns' Monitor dashboard (`MonitorDashboardPage.tsx`) was built with an 8-tab workspace strip ("1. Outbound Voice" through "8. Inbound Chat") and no `overflowMenu` at all — at any width narrower than all 8 tabs' combined natural width, the row would have just clipped, with zero responsive behavior, the same category of gap `TabList`'s "compact" measurement mode was originally built to close for `InteriorPanel`'s tabs (see "TabList's overflowMenu needed a content-aware mode" above) — except this time the fix (the prop itself) already existed and simply wasn't turned on. Fixed by adding `overflowMenu` to that `TabList`. General rule, now also in both repos' CLAUDE.md: every new `TabList` gets `overflowMenu` unless it already has its own documented alternative collapse strategy — treat leaving it off as the thing that needs justifying, not turning it on.

### `TabList` + `overflowMenu`: don't patch the component to make `className` reach the collapsed row — wrap it instead, per the existing pattern
Turning on `overflowMenu` for the Monitor dashboard (see the entry above) needed the tab row to also stretch full-width alongside a trailing "+" button. First attempt patched `tabs.tsx` itself: added an explicit `w-full` to both outer-wrapper branches (`"wide"`'s `.lyra-tab-overflow-wrap` div, `"compact"`'s measurement wrapper) and rerouted the consumer's `className` from the inner `role="tablist"` row onto that outer wrapper instead, reasoning that `className="flex-1"` landing one DOM level too deep (on the inner row, not the actual flex item in the surrounding row) was the bug. That reasoning wasn't wrong about the mechanism, but it was the wrong fix: **the user reported the result still didn't work**, and re-checking turned up an existing, already-correct answer to this exact problem sitting in the codebase — `lyra-form-generator`'s `FormDetailPage.tsx` (its Settings panel tabs), which documents in its own comment that a `className` passed straight to `TabList` only ever reaches the full (uncollapsed) row, never the collapsed "active + N more" row, since `overflowMenu` renders them as two separate siblings inside `TabList`'s own internal wrap div — and solves it by wrapping `TabList` in a plain consumer-owned `<div>` and putting the shared layout classes (there: `px-4`) on *that* div instead, so they apply to whichever of the two rows is actually showing. This is a real, working, already-established pattern — not a gap needing a source fix.
**Reverted**: all three `tabs.tsx` edits (both `w-full` additions, the `!overflowMenu &&` className guard) were undone back to the original source. **Re-applied correctly**: Outbound-Campaigns' `MonitorDashboardPage.tsx` now wraps its `TabList` in `<div className="flex-1 min-w-0">...</div>` instead of passing `className="flex-1"` to `TabList` directly — `min-w-0` matters here too (same family of gotcha as the table-resize entries' own note on it): a flex item's default automatic minimum width would otherwise refuse to shrink below the tab row's natural content size, defeating the entire point of `overflowBreakpoint="compact"`'s "collapse only once it doesn't actually fit" measurement.
**Lesson**: when something doesn't work, re-check for an existing, already-working answer to the exact same problem elsewhere in the codebase before reaching for a source-level patch — `grep`ing for the prop/pattern in question (`overflowBreakpoint`, in this case) across every repo would have surfaced `FormDetailPage.tsx`'s own solved version of this immediately, before any `tabs.tsx` change was made at all.

### Tab strips are pinned to the top of their container — never part of its own scroll
Standing rule: a page or panel's tab strip stays fixed to the top of whatever it's scrolling inside of; only the content below it (a page header, cards, form fields, whatever the tabs are switching between) scrolls. Concrete fix, Outbound-Campaigns' Monitor dashboard (`MonitorDashboardPage.tsx`): the page's outer root originally had `overflow-y-auto` directly on itself, with the workspace tab strip as just another normal-flow child alongside the page header and card grid — so scrolling the page to see the lower cards scrolled the tabs out of view along with everything else. Fixed by moving `overflow-y-auto` off the root and onto a new inner wrapper that holds everything *except* the tab strip, with `shrink-0` added to the tab strip itself (a sibling, not a child, of that scrolling wrapper) so it never shrinks or scrolls away. General shape: `<div class="flex flex-col overflow-hidden">` (root) → `<tab strip shrink-0>` + `<div class="flex-1 overflow-y-auto">…everything else…</div>`. Apply this to every tab bar sitting above scrollable content, not just this one page.

### `TabList`'s "wide" mode gained its own scroll-with-chevrons state, for the gap between "fits" and "collapsed at ≤991px"
The Monitor dashboard's workspace tabs were switched from `overflowBreakpoint="compact"` back to the default `"wide"` (per request — `"compact"` stays available on `TabList` for narrow/resizable hosts like a docked or interior panel, just isn't used for this page-width tab bar). That exposed a real gap `"wide"` mode had: above its fixed ≤991px collapse threshold, the full tab row had no overflow handling at all — if the tabs' natural width ever didn't fit the row's actual available space (a case distinct from "the row dropped to ≤991px"), they'd just silently clip or overflow with nothing to do about it.
**Fix**: `"wide"` mode's full row (`.lyra-tab-overflow-full`, tabs.tsx) is now horizontally scrollable on its own — `overflow-x-auto` + `lyra-scrollbar-hide` (the existing hidden-scrollbar utility, reused rather than re-derived) — with a `ResizeObserver` + `scroll` listener tracking whether the row currently overflows (`tabOverflow`) and, if so, which direction still has room (`canScrollLeft`/`canScrollRight`). Left/right chevron buttons render at each end of the row only when `tabOverflow` is true, each disabled once there's nothing further that way. Clicking a chevron scrolls to the *next actual tab's own edge* (`scrollTabsBy`, walking `[role="tab"]` elements' `offsetLeft`/`offsetWidth`) rather than a fixed pixel amount, so "one click" always means "one tab" regardless of how wide any individual tab is. Native scroll (trackpad, click-drag, keyboard-driven focus scrolling a tab into view) all still work independently of the chevrons — they're an explicit affordance, not the only way to scroll.
The chevrons and the collapsed "N More" row are mutually exclusive by construction: once the row's own width actually drops to ≤991px, the existing CSS container query hides `.lyra-tab-overflow-full` (now also wrapping the chevrons, not just the tab row — moved the class onto a new wrapping div for exactly this) in favor of the collapsed 2-slot row, same as before this change.
**Scope check**: this only activates for `overflowMenu` with the default `overflowBreakpoint="wide"` — `isCompact`'s own render path and the plain (`!overflowMenu`) path are unaffected, and the one other real consumer of `overflowMenu` at `"wide"` (agent-next-gen-v1's Desk tab bar, 6 short labels) still builds clean; its tabs are unlikely to ever actually overflow in practice, so this is additive/dormant there rather than a visible change.

### Follow-up bug, caught from a screenshot: chevrons never appeared — `.lyra-tab-overflow-wrap` had no explicit width
Right after landing the chevron feature above, a screenshot showed the Monitor dashboard's tabs wrapping their own label text onto 2–3 lines each, overlapping the lock icons — no chevrons, no scrolling, nothing like the intended behavior. Root cause: `.lyra-tab-overflow-wrap` (the outer div `"wide"` mode wraps everything in) carries `container-type: inline-size` but had no explicit width of its own — the exact same gotcha this file's own "A `container-type: inline-size` root needs an explicit `w-full`" entry already documents elsewhere (an element with size containment can't use its own content to determine its size, so it can collapse toward zero even while nested in a flex ancestor that's supposedly stretching it). This is a *different* bug from the one fixed in the "TabList + overflowMenu" entry above it — that one was about *where a consumer's `className` lands*; this one is about `TabList`'s own unconditional markup never getting a real width at all, independent of anything a consumer passes in. Fixed by adding a plain, unconditional `w-full` to `.lyra-tab-overflow-wrap`'s own div (and, for the same latent reason, to `"compact"` mode's wrapper div too, even though it isn't currently in use on this page) — critically, *without* reintroducing the reverted `className`-routing change; the two fixes are independent and this PR only needed the first one. General lesson: a `container-type: inline-size` element needs its own explicit width unconditionally, in the component's own base classes — it can't be left for a consumer's `className` (or a flex-stretch ancestor) to provide, because it may not be provided at all, or a consumer relying on the wrapping-div pattern (per the entry above) has no way to reach this specific inner element anyway.

### `TabList`'s horizontal inset always goes directly on `TabList` itself, never a wrapping div — new standing rule
**Incident**: Outbound-Campaigns' Monitor dashboard removed a trailing "+" (add tab) button from its workspace-tab strip and needed the tab row to visually span the page. First attempt put `px-4` on the *wrapping* `<div>` around `<TabList>` (mirroring the older "TabList + overflowMenu" wrapping-div pattern used for `flex-1`/layout classes elsewhere in this file) — the user caught it in a screenshot: the tabs' own bottom divider line stopped short of the page edges, inset along with the tabs themselves, instead of running the reference (`lyra-ux-templates`' `DesktopDesignsPage.tsx`) screenshot's full-bleed line. The user then stated this as a standing rule going forward, not a one-off fix: **"tabs should always build like this — never have the padding on the outside of the line."**
- **Why the wrapping-div placement is wrong**: `TabList`'s own root element (`tabs.tsx`, `role="tablist"` div) already carries `border-b border-lyra-border-subtle`. A `border` sits *outside* `padding` in the CSS box model — so padding placed on a separate ancestor div insets that div's entire box, border included, while padding placed directly on `TabList`'s own element only pushes its `Tab` children in from the edges, leaving its own border spanning the full box regardless. `lyra-ux-templates`' `DesktopDesignsPage.tsx` already does this correctly: `<TabList overflowMenu className="px-6">` — no wrapping div at all.
- **Real gap found and fixed while making this reliable**: `overflowMenu` renders two DIFFERENT sibling elements depending on width — the full (uncollapsed) row, and a separate "active tab + N More" collapsed row (`collapsedRowEl`) below ~991px or once measured content doesn't fit. Before this fix, a `className` passed to `TabList` only ever merged onto the full row's own element — `collapsedRowEl` had its own separate hardcoded class string with no way to receive it, so the inset (and the "border always full-bleed" guarantee) would silently vanish the moment a tab strip actually collapsed. Fixed at the source: `collapsedRowEl`'s className now also runs through the same `cn(..., className)` merge as the full row. This is NOT a repeat of the earlier reverted "TabList + overflowMenu" source patch (that one tried to reroute `flex-1`/layout sizing classes onto a new outer wrapper div and didn't work) — this is a narrower, additive fix: the same consumer `className` now reaches both of `TabList`'s own existing sibling elements instead of just one, no new wrapper/prop/structural change involved.
- **Fix in Outbound-Campaigns**: `MonitorDashboardPage.tsx`'s tab-strip wrapping `<div>` lost its `px-4`; `<TabList className="px-4" overflowMenu overflowBreakpoint="wide">` now carries the inset directly.
- Verified: `tsc --noEmit` in lyra-ui (clean, same 2 pre-existing unrelated errors) and `vite build` in Outbound-Campaigns, `agent-next-gen-v1`, `lyra-ux-templates`, and `lyra-form-generator` (all clean transforms — this only adds a className merge to an element that previously ignored it entirely, so no existing consumer's rendered output changes unless they already pass `className` to an `overflowMenu` `TabList`, in which case they now get the fix, not a regression).

### `TabList`'s "wide" chevron/scroll state was unreachable for short-label tab sets — per-tab shrink absorbed the overflow signal before it could fire
**Report**: "I'm still not seeing the overflow chevrons — at what container width do they appear?" for Outbound-Campaigns' 8-tab Monitor workspace strip, at a width where every tab's own label was already visibly truncating ("Outb…", "Ble…", "Inb…").
**Root cause**: `Tab`'s own button has `min-w-0` and its label has `truncate` — so as the row narrows, the default flex-shrink (1) just keeps compressing each tab's own label down toward nothing instead of the row ever producing genuine overflow. `tabOverflow` (the chevrons' trigger) only flips true once `tablistEl.scrollWidth > clientWidth` — but with every tab free to shrink all the way down to an icon + a sliver of an ellipsis, that "genuinely doesn't fit even at minimum" floor for an 8-short-label row works out to roughly 650–700px total — well *below* the `≤991px` threshold where `overflowBreakpoint="wide"` already collapses the row to "active tab + N More" instead. Mechanically, there's no width where the row is both still above 991px and genuinely out of room: it goes straight from "labels quietly truncating, technically still fits" to "collapsed," and the chevron/scroll state never gets a chance to fire — not something that would resolve at a narrower width, since the collapse threshold is always reached first.
**Fix, two parts** (`tabs.tsx`):
1. **`Tab` gained a `max-w-[22ch]` cap** on its own base classes — a hard ceiling on any single tab's rendered width (independent of available row space) so one unusually long label can't dominate a row on its own. `ch` approximates "character count" across variable-width fonts. Confirmed via a repo-wide scan that no existing `<Tab>` usage in any of the five repos currently has a label ≥22 characters in a normal (non-demo) state, so this doesn't newly truncate anything that previously displayed in full.
2. **`overflowMenu overflowBreakpoint="wide"` now also adds `[&>[role='tab']]:flex-shrink-0`** to the full (uncollapsed) row, disabling each tab's own shrink so it stays at its real (capped) width instead of compressing. This lets the row's true content width genuinely exceed the available space while still above 991px, so `tabOverflow` fires and the chevrons appear exactly where the design always intended them to. Confirmed Radix's `Tooltip` (`asChild`) clones the button directly with no wrapper element, so `[&>[role='tab']]` really does target each `Tab`'s own button as a direct child of the row — same mechanism the pre-existing `[&>[role='tab']]:px-0` selector already relied on.
**Two follow-up corrections, both caught by the user before they shipped as bugs**:
- *"max-width should not apply to full width tabs"* — `fullWidth` mode's whole point is equal-width flex-1 columns that stretch to fill the row; a fixed 22ch cap would fight that the moment a column's fair share exceeds ~22 characters.
