# Lyra UI — Project Summary (June 1, 2026)

## Overview
Lyra is the NICE CXone design system component library built with React 19, TypeScript, Vite 6, Tailwind CSS 3.4, and Storybook 8.4. It uses Radix UI primitives for atoms and CSS custom properties for theming (light/dark via `[data-theme="dark"]`).

There are three repos:
- **lyra-ui** — the component library with Storybook
- **lyra-ux-templates** — lighter consuming page templates project
- **agent-next-gen-v1** — the primary/more feature-complete consuming app

## Architecture
- Tailwind preset (`src/tailwind-preset.ts`) maps CSS variables to utility classes
- Design tokens live in `src/styles/lyra-tokens.css` (light + dark themes)
- Storybook fallback tokens in `src/storybook.css`
- Tailwind config at `tailwind.config.js` (must mirror preset for Storybook)
- Components export from `src/index.ts`
- **Global Storybook dark mode toggle** (`.storybook/preview.ts`): a `Theme` toolbar control (sun/moon icons, Light/Dark) backed by `globalTypes.theme` + a `withTheme` decorator. The decorator sets `data-theme` on the preview iframe's `document.documentElement` — the exact same attribute every component already reads/writes (`AgentProfile`'s dark-mode toggle, `LoginCard`, `AgentNextGenPage`), so every story renders in real dark mode CSS, not just a background-color swap. It also syncs the canvas background to the live `--lyra-color-bg-surface-shell` value so the story canvas itself isn't left mismatched (stark white behind dark components). The toolbar is available globally in every story — no per-story opt-in needed. The existing `backgrounds` addon (`lyra-base`/`lyra-shell`/`dark` swatches) is unrelated and still independently selectable, though for real dark-mode testing use the new Theme toggle, not the `dark` background swatch (which only changes the canvas color, not the tokens).
  - **Gotcha**: the DOM mutation (`setAttribute("data-theme", ...)`) must happen directly in the decorator function body, not inside a `useEffect`. Storybook invokes decorators as plain functions rather than properly-mounted React components, so a `useEffect` called directly inside one isn't guaranteed to fire/re-fire when the toolbar global changes — the toolbar visibly toggled to "Dark" but nothing in the canvas actually re-themed. Fixed by making the `setAttribute`/background-sync call a synchronous side effect in the decorator body itself, which reruns every time Storybook re-invokes decorators (i.e. every toolbar change). If a future dark-mode-adjacent decorator needs to be added here, keep this pattern — don't reach for hooks inside `decorators` entries.
  - **Not covered**: the `Colors` story's `Swatch`/`AliasRow` helpers render hardcoded hex strings via inline `style={{ backgroundColor: value }}`, not CSS variables — they don't (and structurally can't) react to the theme toggle. That page already shows both light and dark hex values side-by-side as static reference chips instead. Use any real component story (Button, Container, Accordion, Toast, etc.) to verify the toggle is working.
- **Storybook never actually loaded the Inter font**: `storybook.css`'s `body` rule always said `font-family: "Inter", ui-sans-serif, system-ui, -apple-system, sans-serif`, but nothing in `.storybook` ever fetched an Inter font file — no Google Fonts link, no self-hosted `@font-face` (the only `@font-face` rules anywhere in this repo are Storybook's own "Nunito Sans" chrome font, unrelated to component rendering). Consuming apps (`lyra-ux-templates`, and any repo scaffolded from it) separately add a Google Fonts `<link>` for Inter in their own `index.html`, so they've always rendered true Inter — Storybook was silently falling back past `"Inter"` to `ui-sans-serif`/`-apple-system` (San Francisco on Mac), confirmed via Chrome DevTools' "Rendered Fonts" panel showing `.SF NS` / `Font origin: Local file` on a `Button` in Storybook. Fixed by adding `.storybook/preview-head.html` with the same Google Fonts `<link>` markup the consuming apps use, so Storybook's own canvas now matches what every real app has been rendering all along. If comparing a component's typography against Storybook in the future, this is now consistent — but for anything touching fonts specifically, sanity-check with DevTools' Rendered Fonts panel rather than assuming a CSS `font-family` value took effect.

## Cross-Repo Sync

This repo is consumed live (no build/version step) by sibling app repos —
currently `agent-next-gen-v1` and `lyra-ux-templates` — via a Vite alias
(`@nicecxone/lyra-ui` → `lyra-ui/src/index.ts`). Those apps always see
whatever is in this source tree the instant it changes; there's no package
version to bump. That means "staying in sync" isn't automatic — it depends
on whether each app's own pages have actually been updated to *use* new or
improved components as they land here, not on any install/build step. A
component can sit unused in this library for a long time after it's added
while consuming pages keep working fine on an older hand-rolled pattern.

**Whenever you're working in this repo** — including right after the user
pulls new changes from GitHub — and you notice a component was added,
replaced, or significantly reworked (check recent entries in this file, or
recent git history), check whether the mounted sibling app folders
(`agent-next-gen-v1`, `lyra-ux-templates`, if present in this session) have
pages still using the older pattern that component replaces. If so,
proactively tell the user what's outdated there and ask whether they'd
like those apps updated — don't silently rewrite their pages. Concrete
examples of this exact situation, already found and fixed once (worth
checking for again after future changes here):
- Hand-rolled `Panel` + `PageHeader` + `TreeMenu` composition where
  `AdminShell` now exists and does the same thing with less code and more
  consistent pin/hover/resize behavior across pages.
- A custom width-animated wrapper (e.g. a `SlidingPanel`-style helper)
  around `AiPanel` instead of using `AiPanel`'s own `draggable` /
  `draggableVariant` prop, which supports docking/undocking and resizing
  out of the box.
- Any component reimplemented locally under a consuming app's
  `src/components/ui/` that now has a shared, more complete equivalent
  exported from `src/index.ts` here.
- A page that never wires up `LeftNav`'s `overlay` prop / narrow-viewport
  handling that other pages in the same app already have.
- Mock "database" fixtures duplicated by hand in a consuming app instead of
  imported from this repo's own fixture files. `src/components/__stories__/
  create-new-agents-data.ts` and `create-new-customers-data.ts` are the
  single source of truth for the CreateNew → Outbound demo's agent/customer
  records; they aren't re-exported from `src/index.ts` (story-only fixtures,
  not real design-system API), so each consumer's `vite.config.ts` adds its
  own explicit `@nicecxone/lyra-ui/agents-data` / `@nicecxone/lyra-ui/
  customers-data` aliases pointing straight at those two files (same pattern
  as the existing `/styles` alias). If a consumer app's `OUTBOUND_AGENTS`/
  `OUTBOUND_CUSTOMERS` are ever hand-written again instead of mapped from
  `CREATE_NEW_AGENTS`/`CREATE_NEW_CUSTOMERS`, that's this same drift
  happening again — fix it the same way.
- **`tailwind.config.js`'s color token list — now a single shared file,
  `tailwind-tokens.cjs`, not hand-duplicated per consumer.** Historically each
  consuming app kept its own full copy of this repo's `theme.extend.colors`
  map (Tailwind configs aren't importable across the plain Vite source alias
  the way components are — `tailwind.config.js` is loaded by Tailwind's own
  config loader, outside Vite, so `@nicecxone/lyra-ui`'s `resolve.alias`
  doesn't apply to it). Adding a new `--lyra-color-*` CSS variable here and
  using it in a component didn't automatically make the matching
  `bg-`/`text-`/`border-` utility class exist in a consumer's build —
  Tailwind silently emits no rule for a class name it doesn't recognize as a
  configured color, so the class sits inert in the DOM with zero visual
  effect. **Found exactly this way**: `agent-next-gen-v1`'s
  `tailwind.config.js` was missing `lyra-status-info-medium`, `lyra-status-
  info-subtle`, and `lyra-status-warning-medium` (present here since long
  before this session) — `channel-row.tsx`'s "highlighted" channel row uses
  `bg-lyra-status-info-subtle`, which therefore rendered with *no background
  at all* in that app, looking like a broken/missing feature (reported as
  "the selected interaction isn't showing") when the actual component logic
  was already correct. A follow-up audit found 31 tokens missing in total,
  including 8 of 10 customer-avatar accent color pairs.

  **Fix (structural, not just a one-time patch)**: the full color map now
  lives in `lyra-ui/tailwind-tokens.cjs` (plain CommonJS, `module.exports`),
  and both `lyra-ui/tailwind.config.js` and `agent-next-gen-v1/
  tailwind.config.js` pull from it via a plain relative `require(...)` —
  `require("./tailwind-tokens.cjs")` here, `require("../lyra-ui/
  tailwind-tokens.cjs")` there — then spread it into their own
  `theme.extend.colors` (each still appends its own one-off literals, e.g.
  `cxone-navy`, locally). There is now exactly one object to keep correct;
  a new token added to `tailwind-tokens.cjs` (alongside its `--lyra-color-*`
  variable in `src/styles/lyra-tokens.css`) is picked up by every consumer
  automatically, with no per-consumer copy step to forget. **Any new
  prototype cloned from `lyra-ui` should do the same** — `require()` this
  file from its own `tailwind.config.js` rather than hand-copying the color
  list — see the "Sync check" section of that new project's own `CLAUDE.md`
  (copied from `agent-next-gen-v1`'s, per the note at the bottom of this
  repo's `CLAUDE.md`).

This file is the single source of truth for *what changed and why* — the
actual check procedure (a `.lyra-ui-sync` marker file recording the last
lyra-ui commit hash each consumer checked against, diffed via `git log`
against this repo's current HEAD) lives in each consumer's own `CLAUDE.md`,
since that's where it needs to run and where it must keep working even if a
consumer repo is opened on its own, without this repo mounted alongside it.
Don't duplicate that procedure here — if it changes, update it in the
consumer `CLAUDE.md`s directly. A repo duplicated from `lyra-ux-templates`
to start a new project inherits both `.lyra-ui-sync` and `CLAUDE.md`
automatically, as long as it keeps `lyra-ui` as a sibling checkout (or its
`vite.config.ts` alias is updated to point at wherever `lyra-ui` lives).

### PhoneInput (`src/components/phone-input.tsx`)
- New `hideCountrySelector` prop (default `false`): renders a plain single-country number field with no flag/dial-code button or country popover. `defaultCountry` / `value.countryCode` still determine the mask and formatting — it just can't be changed from the UI.
- Implementation shares one `numberInput` JSX node between the `hideCountrySelector` shell and the full popover-based shell, so the two layouts can't drift apart.
- Story: `Atoms/PhoneInput` → `Without country selector`

### FilterChip (`src/components/filter-chip.tsx`)
- Uses the `Select` component internally (not a custom dropdown)
- Props: `label`, `options`, `selectedValues`, `onSelectionChange`, `error`, `disabled`, `onRemove`, `className`
- Four variants: default, active, error, disabled
- Removable variant: pass `onRemove` — renders X button with split border-radius
- Chip height: fixed 32px (`h-8`)
- Default bg: `control-subtle`, active bg: `active-subtle`
- Hover/pressed states use proper tokens (hover-active-subtle, pressed-active-subtle for active; hover-critical-subtle, pressed-critical-subtle for error)
- Values truncate at 200px max-width
- Select dropdown uses `portalDropdown` prop to escape overflow containers

### Select (`src/components/select.tsx`)
- Supports: `multiple`, `searchable`, `showSelectAll`, custom `trigger` (button element or icon)
- `dropdownAlign`: "left" | "right" for trigger-based dropdowns
- `portalDropdown`: renders dropdown via `ReactDOM.createPortal` to escape overflow containers
- When trigger is a `<button>` element, it's cloned directly (not wrapped in another button)
- "Select All" row is a `<button>` so clicking text toggles selection
- Dropdown positioned with `top-full` to appear below trigger

### TableToolbar (`src/components/table.tsx`)
- Declarative filter API: `filterDefs`, `filterValues`, `onFilterChange`, `onFilterClear`
- Also accepts `filters` as ReactNode for custom filter content
- Filters render inline to the right of Quick Search (same row)
- Record count props still available but not used in Data Management
- Renders FilterChip components and a ghost "Clear" button internally

### Table (`src/components/table.tsx`)

- Non-autofit uses `overflow-auto` class conditionally
- `useTableGrouping` hook for grouping — must receive filtered data, not raw data

### Button (`src/components/button.tsx`)
- Sizes: sm (24px), default/md (32px), lg (36px), xl (40px), icon-sm (24px), icon/icon-md (32px), icon-lg (36px), icon-xl (40px)

### Divider (`src/components/divider.tsx`)

- Vertical orientation requires a parent with a defined height (e.g. `flex items-center h-6`) to be visible, same constraint as the existing internal `w-px`/`h-full` separator divs
- Stories: `Atoms/Divider` → `Horizontal`, `Vertical`

### Accordion (`src/components/accordion.tsx`)
- `AccordionItem.title` and `.subhead` are typed `React.ReactNode` (widened from `string`) so an item's header can hold richer content — e.g. a name + status `Tag` pill on one line and a multi-line summary on the next — while staying backward compatible with existing plain-string usage.
- Built on the same `CollapsiblePanel` (from `tree-menu.tsx`) used internally elsewhere for smooth open/close; `item.content` can be any React node, including a full `Table`.
- Used in `lyra-ux-templates`' `AgentNextGenPage.tsx` for the home screen's "Latest Contacts" list: each contact is an accordion item (rich title/subhead built from the same fields the old `ListItem`-based version used) whose content is a per-contact interaction-history `Table` (Default `Table` story markup: `TableHeader`/`TableRow` with `hover:bg-transparent`, `flex-[n]` sized `TableHead`/`TableCell` pairs, kebab "More options" button in the last column) wrapped in a fixed-height bordered/rounded container sized to its row count.
- Story: `Atoms/Accordion` → `Rich Header + Table Content` demonstrates the ReactNode title/subhead + embedded `Table` pattern for future reference — check this story before building another "list of expandable rows with a table inside" pattern instead of re-deriving it from scratch.

### Tag (`src/components/tag.tsx`)
- **Bug fix**: every variant's border (`default`, `success`, `warning`, `critical`, `info`) used Tailwind's slash opacity-modifier syntax on a design-token color, e.g. `border-lyra-status-success-strong/30`. Tailwind can only generate opacity-modified utilities for theme colors defined as raw RGB/HSL channel triples — our tokens are CSS custom properties holding full hex/rgba strings (see `lyra-tokens.css`), so that modifier silently produced *no matching CSS rule at all*. The border then fell back to Tailwind Preflight's default (`#e5e7eb` gray) instead of a tinted status color, making every Tag render with a washed-out gray border regardless of variant — visually generic enough that it read as "not a real design-system component" even though it was.
- Fixed by switching those five border classes to a `color-mix()` Tailwind arbitrary value instead, e.g. `border-[color-mix(in_srgb,var(--lyra-color-status-success-strong)_30%,transparent)]` — this works with any color value (not just RGB/HSL triples) and doesn't depend on Tailwind's theme-opacity plumbing.
- This bug affected every consumer of `Tag` (both `lyra-ui` Storybook and `lyra-ux-templates`), not just one app — confirmed by direct Tailwind CLI compilation showing the `/30` classes never emitted a rule while the plain (no-modifier) equivalents did.
- **Takeaway for future components**: don't use Tailwind's `/opacity` modifier on any `lyra-*` color utility — none of our design tokens support it, since they're all plain `var(--lyra-color-*)` references to hex/rgba strings. Use the `border-[color-mix(in_srgb,var(--lyra-color-x)_N%,transparent)]` (or `bg-[color-mix(...)]`) arbitrary-value pattern instead whenever a translucent tint of a token is needed.

### AgentProfile (`src/components/agent-profile.tsx`)
- **Bug fix**: the status-picker popover's "Search statuses" field was a hand-rolled `<input>` (not the real `Input` component), styled with `focus:ring-2 focus:ring-lyra-border-focus`. `lyra-border-focus` maps to `--lyra-color-border-focus-default`, which is intentionally *swapped* between light and dark themes (`#185ba4` blue in light, `#facb33` gold/amber in dark — see the matching `[data-theme="dark"] .focus-visible\:ring-lyra-border-focus` override in `lyra-tokens.css`) because it's meant as a general keyboard-focus-visible indicator for interactive controls (buttons, menu items, tabs), not a text-field focus style. Every real text input (`Input` component) instead focuses with `border-lyra-border-active` + `ring-lyra-border-active/20`, which stays blue in both themes. Using the wrong token made this one search box flash an unexpected gold/orange ring in dark mode while every other input in the app stayed blue.
- Fixed by replacing the hand-rolled `<input>` + absolutely-positioned `Search` icon with the real `Input` component and its `startIcon` prop (`<Input startIcon={<Search .../>} .../>`), which both matches every other text input's focus styling automatically and removes ~10 lines of duplicated markup.
- **Takeaway**: `lyra-border-focus` / `ring-lyra-border-focus` is for keyboard-focus-visible indicators on non-field interactive elements, not text inputs — a hand-rolled input reaching for "the focus color" will likely grab the wrong one. Always use the real `Input` component (with `startIcon`/`endIcon` for icons) for any text field rather than a bespoke `<input>`.

### InteractionNavItem (`src/components/interaction-nav-item.tsx`)
- Represents an active customer interaction as a LeftNav item — a compact colored-initials avatar tile when the rail is collapsed, a full detail card (name, kebab + collapse buttons, message preview, channel + elapsed-time footer) when the rail is expanded.
- `expanded` mirrors `AddChannel`'s prop of the same name/purpose: false → compact avatar tile (rail collapsed), true → full card (rail expanded). Wire it to the same `open` state used for the parent `LeftNav`.
- Initials are derived from `customerName` (first + last name initial, e.g. "Sofia Martinez" → "SM"); with no `customerName`, both the initials and the expanded card's title fall back to `"C"` / `"Customer"`.
- `awaitingResponse` (customer sent a message the agent hasn't replied to yet) switches the avatar/card accents from primary (`bg-lyra-status-info-subtle` / `text-lyra-status-info-strong`) to critical (`bg-lyra-status-critical-subtle` / `text-lyra-status-critical-strong`) and adds a small red badge dot on the compact avatar. No `awaitingResponse` → primary, no badge. Uses the existing `status-*-subtle`/`status-*-strong` token pairing (same convention as `Tag`'s variants), not one-off colors.
- `active` (currently-open interaction) gets an elevated white background + shadow in compact mode, and a `border-lyra-border-active` blue border + elevated background in expanded mode.
- The outer element is a `<div role="button" tabIndex={0}>`, not a real `<button>`, because the expanded card contains its own nested `<button>`s (each channel row's kebab) — buttons can't legally nest inside buttons in HTML, and the compact tile uses the same element type for consistency even though it has no nested controls. (A chevron/`onCollapseClick` button was removed from the expanded card's header row early on; the header row itself no longer has any button at all — see the kebab-menu bullet below.)
- **`LeftNav` gained a new `header` prop** (`src/components/left-nav.tsx`) to host a list of these above the regular nav items — mirrors the existing `footer` prop (used for `AddChannel`) exactly, including the same overlay-mode `React.cloneElement(..., { expanded: hoverOpen })` auto-injection; in inline mode, the consumer passes its own `expanded={open}` on each item, same as `footer` already does for `AddChannel`. Added `items-center` to both `header`/`footer` wrappers so compact tiles center correctly in the 52px collapsed rail width.
- Demonstrated in `LeftNav.stories.tsx`'s "Agent Next Gen Left Nav" story via `header`: an active + awaiting-response item, an inactive + awaiting-response item, and a no-`customerName` + not-awaiting item (showing the `"C"` fallback and primary/no-badge state).
- **Also has its own dedicated `InteractionNavItem.stories.tsx`** (`UI/InteractionNavItem`, 8 stories: Compact/Expanded × active/inactive/no-customer, plus a stacked preview of each mode). Being embedded inside another component's story (here, "Agent Next Gen Left Nav") does **not** make a component browsable on its own in Storybook's sidebar — every standalone component needs its own `ComponentName.stories.tsx` too, same as `AddChannel` has both its own stories file *and* an appearance inside that same Agent Next Gen story. Forgetting the dedicated file was reported back as "I don't see it in the storybook."
- Compact tile follow-up: added a `border` matching the avatar's tone (`border-lyra-status-critical-strong` / `border-lyra-status-info-strong`) around the avatar square, sized to 32×32px (`h-8 w-8`, down from an original 44px), radius `rounded-lyra-sm` (6px, matches every corner in the component — outer wrapper, avatar square, expanded card, kebab button), initials at `lyra-body-sm-emphasis` (12px), and the awaiting-response badge dot fixed to true 12×12px (`h-3 w-3` at `-right-1 -top-1` — `h-3.5`/`w-3.5` is 14px, not 12px, a mixup documented in Important Patterns below).
- **Multi-channel support**: replaced the single `channelIcon`/`channelLabel`/`preview` props with `channels?: InteractionChannel[]` (`{ type, elapsed, preview?, current?, awaitingResponse?, removable?, menuItems? }` — see `ChannelRow` below for what `type` does and why icon/label were dropped from this shape). A customer can have more than one open conversation (e.g. Chat + Email + SMS + WhatsApp simultaneously); the compact tile shows a numeric count badge (top-left, only when `channels.length > 1`, reusing `ActionIconButton`'s exact 18px badge classes since it needs to fit a legible digit — unlike the 12px awaiting-response dot, which has no text) and the expanded card dispatches each channel to its matching per-type row component, with a `border-t` divider between rows (handled via each row's own `isFirst` prop, not the parent's `i > 0` check).
- **`current` + `active` interaction**: a channel row only gets the blue highlight (`bg-lyra-status-info-subtle`) when `active && channel.current` — i.e. an inactive `InteractionNavItem` never highlights any of its channel rows, even if one is flagged `current`, matching an explicit requirement ("the background of the active channel should only be blue on the active cards, the other cards should look plain").
- The expanded card's preview text moved from a single top-level paragraph to living inside each channel's own row (`ch.preview`), since each channel can have a different message/preview once there's more than one.
- `InteractionChannel` also gained its own `awaitingResponse?: boolean` (separate from the card-level `awaitingResponse` prop): the specific channel awaiting a response gets a `critical` (red) chip via `tagVariants({ variant: ch.awaitingResponse ? "critical" : "success", shape: "pill" })` instead of `success` (green), and the expanded card's outer border is `border-lyra-status-critical-strong` whenever the card-level `awaitingResponse` is true — taking priority over the `active` blue border (an active card that's also awaiting response still shows the red "needs attention" border; `active` only continues to control the elevated shadow).
- Hover behavior: the outer expanded card no longer has its own `hover:bg-lyra-state-hover` — hover is scoped to each individual channel row instead (skipped on whichever row is already highlighted `current`+`active`), while the whole card remains one clickable unit — channel rows don't call `stopPropagation`, so clicking anywhere (including inside a specific channel row) still bubbles up to the single `onClick`, which should navigate to that customer's last-active channel, not a per-row destination.
- The compact tile's elapsed-time label now uses the new `lyra-body-xs` preset (see below) instead of `lyra-body-sm`.
- `elapsed` is always a 4-digit `MM:SS` string (e.g. `"00:02"` = 2 seconds since the customer's last response), consistently in both compact and expanded modes — all story examples (`InteractionNavItem.stories.tsx` and `LeftNav.stories.tsx`'s "Agent Next Gen Left Nav") use this format for both modes. An earlier pass had compact using `MM:SS` (`"08:27"`) and expanded using a relative label (`"8m"`) — that inconsistency was corrected; don't reintroduce a relative-label format for either mode.
- **Kebab (⋮) dropdown menu**: each channel row's trailing button (formerly a `Trash2` remove icon, gated by `ch.removable !== false`) is a real dropdown trigger built on the shared `Menu` component. This — along with the row markup itself, the per-type icon/label, and the default menu items — now lives entirely in `channel-row.tsx`, not `interaction-nav-item.tsx`. See the dedicated `ChannelRow` section below.
- `onRemove` was removed from `InteractionChannel` entirely (it was `@deprecated` and unused after the trash→kebab change; the type was rebuilt from scratch for the `type`-based channel-row split, so there was no reason to keep the dead field around).

### ChannelRow (`src/components/channel-row.tsx`)
- **Extracted from `interaction-nav-item.tsx`** so kebab-menu behavior can be owned per channel type at the component level, instead of being configured generically from `InteractionNavItem`'s props or from within a story. Direct trigger: "there will be different kebab menu items and functionality depending on channels and I want to control that at a component level not merely within the InteractionNavItem stories."
- `InteractionChannel.icon`/`.label` (free-form `ReactNode`/`string`, previously supplied by each story) were replaced with a single required `type: "chat" | "email" | "sms" | "whatsapp" | "voice"` (`ChannelType`). The icon and label are no longer story/consumer-supplied — they're baked into each type's row component, so every `InteractionNavItem` consumer renders visually identical Chat/Email/SMS/WhatsApp/Voice rows without having to re-supply the same icon+label every time.

### Chart / DonutChart (`src/components/chart.tsx`, `src/components/donut-chart.tsx`)
- Added to back `agent-next-gen-v1`'s home-screen Activity card (Available/Working/Unavailable ring, replacing the old Schedule summary card). First tried `recharts`, then `c3` (rejected: c3's `d3@^5` dependency carries 9 high-severity vulnerabilities with no non-breaking fix, and c3 itself is effectively unmaintained) before settling on **ECharts** via `echarts-for-react`, per explicit user direction since more chart types are coming and engineering may revisit the choice later — picked for being actively maintained with a wide chart-type catalog, so the next chart type needed is very likely already covered rather than requiring another library swap.
- **`Chart`** is a deliberately dumb wrapper around `echarts-for-react` — takes a raw ECharts `option` object and renders it, nothing else. This is the shared base every future ECharts-backed component should build on rather than each hand-rolling its own `ReactECharts` usage.
- **`DonutChart`** is the first concrete chart built on `Chart`: a ring given `data: { label, value, colorVar }[]`. Deliberately renders only the ring, no built-in legend — a consumer that wants a legend (like the Activity card's colored-dot + label + percent rows) builds it from the same `data` array alongside the chart, so `DonutChart` stays reusable for any "ring + external legend" layout rather than being locked to one card's exact look. See `DonutChart.stories.tsx`'s `AllVariants` → "Ring + external legend" for the reference composition (`showTooltip={false}` on the chart since the external legend already shows every value).
- **Canvas color gotcha (read before adding any other canvas-based chart)**: ECharts renders to `<canvas>`, and the Canvas 2D API cannot resolve CSS custom properties — `ctx.fillStyle = "var(--lyra-color-status-success-strong)"` is silently invalid and paints black instead of erroring. Every lyra token color handed to ECharts has to be resolved to a concrete value via `getComputedStyle(document.documentElement).getPropertyValue(...)` first. `DonutChart` does this itself (`resolveCssColor`) and re-resolves whenever `document.documentElement`'s `[data-theme]` attribute flips (via a `MutationObserver`, exposed internally as `useThemeVersion`) — without that, a chart's colors would go stale the instant a user toggled dark mode, since the resolved hex values were only ever computed once at first render. Any future Chart.js/ApexCharts/etc. component needs this same treatment; it is not automatic the way it is for every DOM-based component's `text-lyra-*`/`bg-lyra-*` classes.
- `data.colorVar` takes the full `var(--token)` string (not a bare token name) so callers can pass any valid CSS color expression, not just lyra tokens, if a future consumer ever needs a one-off color.
- Adds `echarts` + `echarts-for-react` as new dependencies. No new vulnerabilities introduced (confirmed via `npm audit` before and after — the only vulnerabilities present are pre-existing dev-tooling ones in Storybook/vite/concurrently, unrelated to this change).
- Stories: `Atoms/Chart` (`Default` bar chart, `AllVariants` bar + line — proves the wrapper is chart-type-agnostic), `Atoms/DonutChart` (`Default`, `AllVariants` → default ring / thinner ring / ring + external legend).
- **Hover state, and a clipping bug it caused**: added `emphasis`/`blur` to `DonutChart`'s pie series so hovering a slice gives real feedback (dim the other slices) instead of nothing. First attempt also used ECharts' `emphasis.scale` (grows the hovered slice outward) — this hard-clipped the slice's outer arc against the canvas edge, because `scale` grows the *actual drawn radius*, not a CSS transform, and the default `outerRadius` ("95%") already left almost no headroom inside the canvas. Fixed by dropping `scale` entirely and using a shadow glow (`itemStyle.shadowBlur`) instead, which reads as "this one's active" without growing the geometry past the canvas bounds. Any future chart with a hover-grow effect needs to leave real radius headroom (well under 95%) if it's going to use `emphasis.scale`.

### LeftNav (`src/components/left-nav.tsx`) — overlay mode's `header`/`footer` didn't actually expand on hover
- **Bug, caught from a screenshot**: in overlay mode (narrow screens — the aside stays a fixed 52px rail with the expanded panel sliding out as an absolutely-positioned overlay on hover), the nav's own item list correctly expanded on hover, but consumer-supplied `header`/`footer` content (`agent-next-gen-v1` passes a `CreateNew` button as `footer` and a `<>` fragment of `CreateNew` + `InteractionNavItem` cards as `header`) stayed visually collapsed the whole time.
- **Root cause**: the overlay branch auto-injects hover state via `React.isValidElement(header) ? React.cloneElement(header, { expanded: hoverOpen }) : header` — this is correct for a *single* element, but `agent-next-gen-v1`'s `header` is a `<>...</>` fragment wrapping multiple elements. `React.isValidElement` returns `true` for a Fragment too (it's a real element, just of type `React.Fragment`), so the clone actually happened — but `cloneElement` on a Fragment attaches the new prop to the Fragment itself, and `React.Fragment` doesn't forward arbitrary props down to its children. The injection silently no-op'd, and each child kept whatever `expanded` value the consumer had already hardcoded on it directly (`expanded={navOpen}`, the *inline*-mode toggle state per the doc comment's "consumers should pass their own `expanded` prop tied to `open` in inline mode" contract) — so in overlay mode the cards tracked `navOpen`, never `hoverOpen`.
- **Fix**: new `injectExpanded(node, expanded)` helper — unwraps one level of `React.Fragment` first (checking `node.type === React.Fragment` and reading `.props.children`) before running `React.Children.map` + `cloneElement` over whatever's left, so it clones every real top-level child whether `header`/`footer` was passed as one element or a fragment of several. Both the `header` and `footer` blocks in the overlay branch now call this instead of the old bare `isValidElement`/`cloneElement` pair. The inline-mode branch is untouched — it never auto-injects `expanded` at all, by design, since inline mode's `header`/`footer` should already carry the consumer's own `open`-driven `expanded` value.
- Scoped entirely to `left-nav.tsx`; no change needed in `agent-next-gen-v1` — the fragment-of-elements pattern it already uses for `header` is a completely reasonable, common React shape, and the bug was in `LeftNav` failing to handle that shape, not in the app doing something unusual.

Its trigger `<button>` stops click propagation (same pattern as `FavoriteButton`/`KebabMenuButton`) so picking a channel doesn't also select the whole card underneath it.
- **The harder half — "keep the same flow for launching the outbound as if it was clicked from the CreateNew button" — is `CreateNewOutboundConfig.launchRequest`/`onLaunchRequestHandled`**, a new deep-link pair: setting `launchRequest: { contactId, channel }` makes `CreateNew` look the contact up across every group's `contacts` (same lookup `allOutboundContacts`/"Favorites" already uses), reset its internal screen stack straight to `[{ kind: "group", groupId }, { kind: "detail", ...contactId, channel }]` (bypassing the group/contact-list screens entirely, unlike `goToDetail`'s normal *push*), seed the detail screen's fields exactly like a normal row click would (`defaultDetailValueFor`, etc.), and open the popover — landing the agent on the exact same "Select Channel / Select Phone / Outbound Skill → Start Interaction" screen a real `OutboundContactRow` click would, just entered from a different starting point. `onLaunchRequestHandled` exists because `CreateNew` can't clear its own prop — the consumer resets its `launchRequest` state back to `null` there so an unrelated re-render doesn't replay the same request.
- **Wired into all three "Agent Next Gen" consumers identically**: each already tracks live interactions keyed by contact id (`ActiveInteraction`/`AgentNextGenDemoInteraction`), so each adds one `outboundLaunchRequest` state variable, passes `launchRequest`/`onLaunchRequestHandled` into `CreateNew`'s `outbound` prop alongside its existing `onStartCall`/`onQuickDial`, and builds an `outboundContactsById` lookup (`outboundConfig.groups.flatMap(g => g.contacts ?? Every `InteractionNavItem` (including quick-dialed/redialed cards and, in `LeftNav.stories.tsx`, the three fixed demo cards with no `outboundContactsById` entry) now always renders `headerAction`; the per-card `addOutboundChannelOptions` falls back to the full unfiltered `OUTBOUND_CONFIG.channelOptions` when there's no matching `contactRecord` to filter against, rather than omitting the button. Selecting a channel from one of these still ends in a no-op inside `CreateNew`'s `launchRequest` effect (there's genuinely no contact to look up), but the button itself is now visually consistent across every card, matching the request.
- **Follow-up bug, reported directly, twice**: "when I click the add from the interactionNavItem header and the channel menu opens then I select a channel the next menu flashes open then closes quickly - it should stay open" — then, after an initial fix attempt, "it's still flashing open then closing." The first fix attempt (an `openedViaLaunchRequestRef` flag paired with deferring the `launchRequest` effect's state changes by one `setTimeout(0)` macrotask) treated the symptom as an auto-focus-*on-mount* problem and did not resolve it, because the real mechanism fires later, on **unmount**.
  - **Actual root cause** (found by reading `@radix-ui/react-focus-scope`'s source directly): every Radix `Popover.Content` mounts a `FocusScope`. On mount it records `previouslyFocusedElement = document.activeElement` (here, the "+" button itself, since `OutboundAddButton`'s own popover already cancels its mount auto-focus via `onOpenAutoFocus`). On unmount, regardless of `trapped`/modal settings, `FocusScope` unconditionally schedules `setTimeout(() => focus(previouslyFocusedElement ?? document.body), 0)` — restoring focus to whatever had it before the popover opened. `OutboundAddButton`'s `Popover.Content` doesn't unmount immediately on `setOpen(false)`; Radix's `Presence` keeps it mounted through its exit animation (`popover.tsx`'s `data-[state=closed]:animate-out duration-100`, ~100ms) before actually unmounting and running that cleanup. By the time the delayed `focus()` call fires, `CreateNew`'s own popover has already opened (via `launchRequest`) and mounted its own `DismissableLayer`, which keeps a **persistent, document-level `focusin` listener** for as long as it's mounted (not just a one-time mount-time check). The delayed `focus()` call fires a real `focusin` on the "+" button — an element outside `CreateNew`'s newly-mounted layer — which that layer's `useFocusOutside` hook reads as an outside focus and immediately dismisses on. That's the "flashes open then closes quickly": `CreateNew` opens, then ~100ms later (`OutboundAddButton`'s exit animation plus its own `setTimeout(0)` cleanup) gets involuntarily closed by a focus event indistinguishable, from `CreateNew`'s own layer's perspective, from a genuine outside click.
  - **Real fix**: add `onCloseAutoFocus={(e) => e.preventDefault()}` to `OutboundAddButton`'s own `Popover` (`create-new.tsx`). This suppresses exactly the delayed refocus-on-unmount behavior described above — `OutboundAddButton`'s flow always hands off to a different surface (`CreateNew`) on selection, so returning focus to the "+" button on close serves no purpose. One line, at the actual source of the problem, rather than working around Radix's mount-time auto-focus (which was never the culprit). The earlier `openedViaLaunchRequestRef`/deferred-`setTimeout` changes in the `launchRequest` effect and the main `Popover`'s `onOpenAutoFocus` were left in place (harmless, and they still correctly distinguish a `launchRequest`-driven open from a normal user click), but they were not what fixed this bug — **no headless browser was available in this sandbox to verify interactively (Playwright's Chromium can be downloaded but not launched, since `--with-deps`/`sudo` are blocked here), so this fix is verified by source-level reasoning plus `tsc`/Storybook/`vite build`, not a live click-through.**
- **New story added**: `InteractionNavItem.stories.tsx` gained `NavItemHeader` ("Header — Add Outbound Button"), composing the real `OutboundAddButton` (imported from `create-new.tsx`) into `headerAction` on a stack of expanded cards — the first story in this file to demonstrate the header/`OutboundAddButton` combination, since every prior story only exercised `InteractionNavItem` in isolation. Deliberately doesn't render a `CreateNew` popover alongside it (no outbound flow to hand off to in a standalone story); `onSelect` just logs the picked channel, to demonstrate the header layout and the button's own tooltip/flyout behavior on their own.

## Important Patterns
- **Text capitalization — use this for any new copy unless the user specifies otherwise:**
  1. Labels (button text, input labels, input placeholders, chip/tag labels, etc.) — first-letter capitalized (each word capitalized, e.g. "Wait Time", "Select Agent").
  2. Body copy — sentence case (only the first word/proper nouns capitalized, e.g. "This channel is already open with this contact.").
  3. Tooltip copy — sentence case, same as body copy.
  4. Header text — first-letter capitalized, same convention as labels.
  Caught in practice on `DashboardQueue`'s "cards" header, which read "Wait time: {wait}" (lowercase "time") while `CreateNew`'s skill-row queue text used the correct "Wait Time" — fixed by capitalizing `DashboardQueue`'s label to match (see the `CreateNew` entry above).
- **Before reaching for a vanilla Tailwind utility (spacing, sizing, radius, etc.) in any lyra-ui component or story, check other lyra-ui stories/components first for the established pattern/token.** Case in point: `InteractionNavItem`'s status badge was sized with raw Tailwind `h-3.5 w-3.5` (intended as 12×12px) — `h-3.5`/`w-3.5` is actually 14px (0.875rem); `h-3`/`w-3` is the one that's 12px (0.75rem). Skipping this check produced a badge that measured 14×14 in devtools when 12×12 was intended, and wasn't caught until the user inspected it directly. Grepping sibling components (e.g. other badge-dot implementations like `ActionIconButton`/`NotificationsBell`) or checking the `lyra-radius-*`/spacing scale before picking a raw utility value would have caught the size mismatch immediately.
- Always reuse existing components (Select, SearchInput, Checkbox, Button) — never rebuild custom versions
- **This applies inside `__stories__` files too, even for a purely illustrative/non-functional example.** The `Menu.stories.tsx` "Width Scale" story's `md` example was first built with a hand-rolled fake search bar (`<div><Search icon /><span>Search…</span></div>`) instead of the real `Input` component — despite the exact same file (`agent-profile.tsx`) it was citing as the real-world reference already using `<Input startIcon={<Search .../>} placeholder="Search statuses" />` right there to copy from. Being non-functional/decorative is not a reason to skip using the real component — fixed by rendering the actual `Input` with the same `startIcon` prop. This is exactly the "composition over reimplementation" rule from `CONTRIBUTING.md` §3 (see also §1, "Use Lyra components as designed — never hard-code"), and it was violated in a story added specifically to document/enforce a different convention (the width scale) in the same sitting — check every element of a story against `src/index.ts`, not just the component the story is nominally about.
- **lyra-ux-templates must import UI atoms from `@nicecxone/lyra-ui`, never from local `src/components/ui/*` reimplementations.** A Login template (Phone Setup card with radio group + phone number field) was first built with ad hoc local copies of Radio/Input/Button/Checkbox in the templates repo. They visually diverged from the real Storybook components (radio dot vs. filled circle indicator, plain text input vs. the real `PhoneInput` with country selector/mask/validation). Fix: always check `lyra-ui/src/index.ts` and that component's `__stories__` file *before* building template UI — use `RadioGroup`/`RadioGroupItem` (`radio.tsx`) and `PhoneInput` (`phone-input.tsx`) directly, both of which already support built-in `label` props (no need to hand-roll `<label>` wrappers). If a lyra-ui component doesn't exist yet for something a template needs, that's a signal to add it to lyra-ui (per Scope Rules below) rather than approximate it locally in the template.
- New Tailwind color utilities must be added to BOTH `tailwind-preset.ts` AND `tailwind.config.js`
- New CSS variables must be added to BOTH `lyra-tokens.css` AND `storybook.css`
- **`.lyra-heading-lg` had drifted out of sync between the two files** (`lyra-tokens.css` had `font-weight: 600`, `storybook.css` and `Typography.stories.tsx`'s docs table both said `500`) — caught by comparing `PageHeader`'s title weight in a real consuming app against lyra-ui's own Storybook side by side. User confirmed `500` (the Storybook/docs value) as correct; fixed by changing `lyra-tokens.css` to `500` to match. This is exactly the kind of two-file drift the "kept in sync" convention above exists to prevent — when comparing a rendered value against "what lyra-ui says," check both files (and the Typography story's docs table) before assuming which one is stale.
- New color tokens should be added to `Colors.stories.tsx` (swatches + alias table)
- **Using the "correct" component isn't enough — the exact markup shape shown in its `__stories__` file matters too.** On the Login template, `Checkbox` was used with its `label` prop (`<Checkbox label="Save Preferences" ... />`), which is valid API but internally wraps the input in an extra `div.flex.items-center.h-5`. Every plain "checkbox + text label" story (`Default`, `Checked`, `Interactive`, `WithSecondaryText`, `StateMatrix`, etc.) instead renders a bare `<Checkbox />` beside a manual `<label className="flex items-center gap-2">…</label>` — the `label` prop path is only ever demonstrated for `Required`/`Readonly` states. Using the prop form produced DOM that didn't match Storybook and looked like a bug. Fix: for a plain labeled checkbox, always use `<label className="flex items-center gap-2 cursor-pointer"><Checkbox .../><span className="lyra-body-md text-lyra-fg-default">…</span></label>`, matching the `Default` story exactly.
- **Every modal's outer card must use `Container variant="modal"`, never a hand-rolled div with its own background class.** The home-screen welcome modal in `lyra-ux-templates` was first built with a plain `<div className="... bg-lyra-bg-surface-base ...">`, while `LoginCard` (also a modal) uses `Container variant="modal"` (`bg-lyra-bg-surface-overlay`). In light mode both tokens are `#ffffff` so the mismatch was invisible; in dark mode `bg-surface-base` is `#1f1f1e` and `bg-surface-overlay` is `#2e2e2e` — visibly different shades of "black," so the two modals looked inconsistent side by side. Fixed by switching the welcome modal to `Container variant="modal"` too. Any new modal should do the same from the start rather than approximating the look with a raw div.

### Post-layout QA checklist (do this before calling any template "done")
1. Open each lyra-ui component's `__stories__/*.stories.tsx` file for every component used in the new layout.
2. For each one, find the story that matches the case being built (plain vs. required vs. readonly vs. grouped, etc.) and copy its exact prop/markup shape — don't just satisfy the TS prop types.
3. Inspect the rendered DOM (e.g. browser devtools) and diff it mentally against the story's structure — watch for extra wrapper `div`s, different class lists, or different parent/child nesting than the canonical story produces.
4. If a prop *could* produce two different DOM shapes for the same visual result (e.g. `Checkbox`'s `label` prop vs. a manual `<label>`), default to whichever shape the majority of stories for that component use, not just whichever is more convenient to type.

### Every data table built from a screenshot/prompt includes baseline Column Options + Refresh
**Always include a Column Options (`ColumnToggle`) control and a Refresh action on any `Table`/`TableToolbar` generated from a screenshot or prompt — even if the reference screenshot doesn't show them.** These are treated as baseline table functionality, not screenshot-specific features: `ColumnToggle` (`actions` slot, wired to a `visibleCols` Set + `allColumnDefs` derived from the column config) and a `refresh` entry in `actionDefs` (icon `RefreshCw`, `onClick` handler), exactly as `DesktopDesignsPage.tsx` demonstrates. Concrete incident: `Outbound-Campaigns`' `OutboundCampaignsPage.tsx` was rebuilt to match a "Campaigns" data-table screenshot that showed neither control, and both were initially omitted to match the screenshot exactly — user corrected this, since matching a screenshot's *content* (columns, data, filters) shouldn't mean dropping standard table chrome the screenshot simply didn't happen to capture. Fixed by adding both back in.

### When a screenshot/prompt doesn't clearly match an existing component
If a prototype's design is being changed from a screenshot or a prompt and either (a) it's unclear which existing lyra-ui component a description in the prompt is referring to, or (b) nothing in lyra-ui visually matches what the screenshot shows, ask the user which component to use, or whether to build something new — don't guess. If "build something new" is chosen, keep the new UI local to the consuming app/prototype; do not add it to lyra-ui's own component library until the user explicitly asks for it to be promoted there. (Mirrors the existing AppMenu-in-new-apps guidance under Known Debt: don't default into a guessed mismatch, and don't default into an unrequested library addition either.)

### Every `lyra-ux-templates` page fades in on load
Every top-level page component in `lyra-ux-templates` (the components rendered directly by `App.tsx`'s router — currently `AgentNextGenPage`, `LoginPage`, `OutboundEngagementPage`, `DesktopDesignsPage`, `ShellPage`, and the shared Header/Sidebar shell in `App.tsx` itself) fades its entire root element in on mount, for a bit of polish rather than content just snapping into view.
- Implementation: add `animate-in fade-in-0 duration-500` to the page's single outermost returned element's `className` (the `tailwindcss-animate` plugin utilities already used elsewhere in both repos for Popover/Overlay/etc. — no extra JS or state needed, it's a plain CSS animation that plays once on mount).
- **When creating any new page/route in `lyra-ux-templates`, add these three classes to its outermost element as part of building it** — don't treat it as optional polish to add later.
- Since React only replays a mount animation when the element/component actually (re)mounts, this only self-triggers correctly if each distinct page is its own component swapped in by the router (as they are here). If a new page is ever nested *inside* another already-mounted page's JSX instead of being a router-level swap, the fade won't retrigger on that inner navigation — put the classes on whichever element actually mounts fresh for that transition.

### After promoting a template block into a real lyra-ui component
When markup that used to live inline in a `lyra-ux-templates` page gets promoted into a proper `lyra-ui` component (e.g. `Divider`, `LoginCard`), that promotion isn't done until every consumer is switched over:
1. Search the templates repo for the old inline markup/text that the new component replaces (e.g. `grep` for a distinctive string or class combo from the old JSX) and confirm zero matches remain — a leftover duplicate is exactly the kind of drift this whole doc exists to prevent.
2. Replace the template's inline implementation with an import of the new component from `@nicecxone/lyra-ui`, passing only the props needed to fit that page (callbacks for routing/navigation, branding overrides, etc.) — the template file should shrink, not stay the same size with an import added on top.
3. Rebuild both repos (`tsc --noEmit` in lyra-ui, `vite build` in lyra-ux-templates) to confirm the swap didn't silently drop behavior.
4. Record the new component in this file's Key Components list (props, defaults, gotchas) so the next pass doesn't have to rediscover them by reading the source.

## Scope Rules
- **Do NOT modify `lyra-ui` core components** (anything under `lyra-ui/src/components/`) unless the request explicitly specifies making changes to lyra-ui. Template and story work in `lyra-ux-templates` should be solved at the template/consumer level.
- When a fix is needed that would normally require a lyra-ui component change, first look for a prop, className, or wrapper approach in the consuming template before touching the library.
- **Always use the shared `app-icon.svg` mark for the "Agent Next Gen" smiley/logo** — it exists identically in both `lyra-ui/src/assets/app-icon.svg` and `lyra-ux-templates/src/assets/app-icon.svg`; import it directly (`import appIcon from ".../assets/app-icon.svg"`) and render it as `<img src={appIcon} ... />`, the same way `AppName`/`AppHeader` and `LoginCard` already do. This is the two-dot-eyes + single blue gradient swoosh mark. Do **not** use `CXoneSmiley` (a visually different, unrelated multicolor rainbow-smile component) or hand-roll a local one-off smiley SVG for this — this exact "used the wrong smiley" mistake has now happened twice (see the `LoginCard` and `CXoneSmiley` entries above); check for the real asset/component and a reference screenshot before assuming which mark is meant.
