# CLAUDE.md

Before creating or modifying ANY component in this repo, read `CONTRIBUTING.md` in full — it's the binding authoring rulebook, not optional background reading. In particular:
- **"Use Lyra components as designed — never hard-code" (§1, the top rule in the document)** — use the real component's actual behavior, even when a design mockup/screenshot shows something different. Never hard-code a value a real component already computes correctly on its own (a placeholder, a formatted value, a default) just to match a static picture. Hard-coding is only acceptable when the user explicitly asked for that exact value, or when no matching component exists yet and one will be built to replace the placeholder later. Concrete incident: `CreateNew`'s dial-pad field hard-coded `placeholder="Enter phone number"`, silently overriding `PhoneInput`'s own correct per-country example placeholder — the fix was to delete the override, not to make the hard-coded string "smarter."
- "Composition over reimplementation" — before writing any new UI logic (a dropdown, popover, menu, list of clickable items, etc.), check whether `Menu`, `Popover`, or another existing primitive already provides it, and compose that primitive rather than hand-rolling parallel markup. A component that reimplements `role="menu"`/`role="menuitem"` behavior instead of rendering `<Menu>` is a bug, not a style choice — it will drift from the real component every time `Menu` changes.
- "Cross-repo sync rule," "Controlled components," "Z-index hierarchy," "Icons," "File naming & location," "Tailwind & theming," and the "New component checklist" — standing conventions for every component in this repo.
- Whenever creating a form or any form-like set of fields (here or in a consuming app), consult `Input.stories.tsx`'s and `Select.stories.tsx`'s own "Default" playground controls first (Label only, With buttons, Buttons position, Button type, Icon buttons, Button size, Button count, Horizontal, Help, Error, Max width) and compare them against the prototype/design being requested — then compose the field from that matching combination of props, instead of hand-rolling markup for a variant one of these controls already demonstrates.
- **A screenshot of an older or differently-styled interface is still asking for the matching real component, not a from-scratch reproduction of its exact shape.** A different corner radius, size, or color from what a component currently looks like is a prop/className detail to reach for *if that component actually supports it* — not evidence a brand-new one is needed. See PROJECT_SUMMARY.md's "A screenshot of an older/differently-styled interface still means 'use the matching real component'" entry (the `OnlineHelpButton` incident: a filled circular icon button read as "needs a new circular launcher component," when it was just `Button`'s existing "default" variant + an icon size).
- **Reusing the right component doesn't automatically mean the right size was picked for it — check that separately.** The same `OnlineHelpButton` incident went through a fabricated size (`h-12 w-12`, not one of `Button`'s real icon sizes at all) and then a real-but-wrong one (`icon-2xl`, the AppHeader-only tier, picked because it "sounded" like the right tier for a launcher button) before landing on `icon-lg` (36px) — the size that actually matches the other buttons in the same rail. See PROJECT_SUMMARY.md's "Picking a real size token isn't enough" entry, right below the one above: after choosing which component to reuse, separately check its actual neighbors' real rendered size and match that specific one.
- **A className override isn't automatically valid just because a screenshot shows it — check whether the component actually supports varying that property at all.** The same `OnlineHelpButton` incident, a third mistake: it also picked up a `rounded-full` override to match the screenshot's rounder corners, but `buttonVariants` (button.tsx) hardcodes `rounded-lyra-sm` identically across every variant and size — there's no circular/pill option in `Button`'s real API to opt into, so `rounded-full` was a fabricated value, not a legitimate override (same failure as the size guesses above, just applied to shape). See PROJECT_SUMMARY.md's "A component's real shape isn't a free-form override either" entry: before adding any override to a reused component, check the component's own source for whether that property is actually meant to vary — a value hardcoded identically everywhere means no override belongs there.
- **Every `TabList` gets `overflowMenu` turned on — no exceptions without a real reason.** `overflowMenu` (tabs.tsx) is what makes a row of tabs collapse to "active tab + N More" instead of clipping/wrapping once it runs out of room; it's off by default (so existing narrower-purpose collapse strategies like `ChannelTab`'s own don't fire early), but that default has repeatedly been mistaken for "responsive collapse is optional" when building a *new* tab bar from scratch. It isn't — every new `TabList` needs it unless that `TabList` already has its own different, purpose-built collapse strategy (per `overflowMenu`'s own doc comment, `ChannelTab` is the one documented exception). Pick `overflowBreakpoint="compact"` over the default `"wide"` specifically when the `TabList` lives somewhere narrow/resizable (a docked or interior panel) rather than a normal page-width tab bar. See PROJECT_SUMMARY.md's "Every TabList needs overflowMenu" entry (Outbound-Campaigns' Monitor dashboard, built without it the first time).
- **Don't patch `TabList` itself to make a layout `className` reach the collapsed row — wrap it in a consumer-owned `<div>` instead, per the existing pattern.** With `overflowMenu` on, `TabList` renders its full row and its collapsed "active + N more" row as two separate siblings inside its own internal wrap div; a `className` passed straight to `TabList` only ever reaches the full row. `lyra-form-generator`'s `FormDetailPage.tsx` already solved this correctly (wraps `TabList` in a plain `<div>` and puts shared layout classes there) — a later attempt to "fix" this at the source in `tabs.tsx` was reverted once it turned out not to actually work and this existing pattern was found. See PROJECT_SUMMARY.md's "TabList + overflowMenu" entry.
- **A tab strip is always fixed to the top of its scrolling container, never part of the scroll itself.** `shrink-0` on the tab row, kept outside whatever wrapper has `overflow-y-auto` — a standing layout rule for any `TabList` sitting above scrollable page/panel content, not something to decide per page. See PROJECT_SUMMARY.md's "Tab strips are pinned to the top of their container" entry.
- **`overflowBreakpoint="wide"`'s full row is horizontally scrollable with chevrons above its own ≤991px threshold — this is built-in, don't re-derive it locally.** If a `"wide"`-mode `TabList`'s tabs don't fit their available width but the row hasn't dropped to ≤991px yet, left/right chevron buttons appear automatically (tabs.tsx) to scroll one tab at a time; native scroll still works too. Nothing needs to be added in a consuming app for this — it's part of `"wide"` mode itself. See PROJECT_SUMMARY.md's "TabList's 'wide' mode gained its own scroll-with-chevrons state" entry.
- **A `container-type: inline-size` element needs its own explicit width unconditionally, in the component's own base classes — never left for a consumer's `className`/flex-stretch to (maybe) provide.** Caught from a screenshot: `.lyra-tab-overflow-wrap` had no explicit width, so it silently collapsed toward zero (an element with size containment can't use its own content to size itself) even while nested in a flex ancestor that looked like it should stretch it — the chevrons above never appeared, tabs just wrapped their own text instead. See PROJECT_SUMMARY.md's "Follow-up bug, caught from a screenshot" entry — a distinct bug from the `className`-routing one right above it, fixed independently.
- **Card/grid layout responsiveness is always container-query-based, never a Tailwind `sm:`/`md:`/`lg:`/`xl:` viewport prefix.** Check for an existing container-query class first (`.lyra-container-grid`, `.lyra-form-grid`, `.lyra-metric-row`, `.lyra-metric-card-grid`, `.lyra-card-split`) and add a new dedicated one — mirrored in both lyra-tokens.css and storybook.css — if none fits, rather than reaching for a viewport breakpoint as a shortcut. See PROJECT_SUMMARY.md's "Card/grid responsiveness must be container-based" entry (the Monitor dashboard's card grid and summary-card split, both built with viewport prefixes the first time).
- **`Tab`'s label truncates + shows a tooltip only when actually truncated — measured, not assumed.** `Tab` always renders its label in a `min-w-0 truncate` span with a `ResizeObserver` comparing `scrollWidth`/`clientWidth`; the wrapping `Tooltip` stays mounted at all times and is toggled via its own `disabled` prop rather than conditionally wrapped/unwrapped — the latter would remount the tab (and its focus/interaction state) every time the truncation state flips. See PROJECT_SUMMARY.md's "Tab truncates its label and shows a tooltip" entry.
- **Labels and header text default to Title Case (every word capitalized — "Wait Time", "Outbound Email"), not sentence case.** Only body copy and tooltip copy are sentence case. See PROJECT_SUMMARY.md's "Text capitalization" entry under Important Patterns — its wording used to say "first-letter capitalized," which reads backwards (like "capitalize only the first letter") and caused a real misapplied fix in Outbound-Campaigns' Monitor dashboard; say "Title Case" instead of "first-letter capitalized" anywhere this comes up.
- **`TreeMenu` supports arbitrary nesting depth — any row (not just top-level) can have its own `children` and expand/collapse itself.** `TreeMenuChild.children`/`defaultOpen` recurse into the same `TreeMenuRow` rendering a top-level `TreeMenuItem` uses (icon-recolor-on-active, chevron, indentation scaling by depth) — don't reach for a second, flat-only tree pattern when a design needs 3+ levels. See PROJECT_SUMMARY.md's "TreeMenu supports arbitrary nesting depth" entry (an "Enterprise" root added above an existing flat category list, which needed to *contain* that list, not sit beside it).
- **`TreeMenu`'s `exactSelection` prop (default `false`) makes selection exact — no parent-active cascade, and any selected row (parent or leaf) gets the same background pill.** Default behavior (cascading parent-active, background pill only on leaves) is still correct for `LeftNav`/`AdminShell`'s own nav trees — only turn this on for a tree meant to have exactly one selected row at a time, at any depth (currently just Outbound-Campaigns' Monitor dashboard side menu). See PROJECT_SUMMARY.md's "TreeMenu gains exactSelection" entry.

Before making changes in this repo (or any sibling repo that has this one mounted alongside it), also read `PROJECT_SUMMARY.md` in full — in particular:
- "Cross-Repo Sync" — checking whether consuming apps (`agent-next-gen-v1`, `lyra-ux-templates`) have adopted recent component changes made here.
- "Important Patterns" and "Scope Rules" — standing conventions for this repo itself (e.g. new Tailwind colors/CSS variables must be added to both their light-DOM file and their Storybook-fallback file; don't reach for a raw Tailwind value without checking existing components/tokens first).
- "After promoting a template block into a real lyra-ui component" — the checklist for finishing a promotion (old markup removed from the template, both repos rebuilt, the new component recorded in this file).
