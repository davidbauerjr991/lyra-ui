# CLAUDE.md

Before creating or modifying ANY component in this repo, read `CONTRIBUTING.md` in full — it's the binding authoring rulebook, not optional background reading. In particular:

## Rule zero: never hand-roll a button

**Every clickable, button-shaped element is `Button`, `ActionIconButton`, or an existing purpose-built button atom (`FavoriteButton`, `PanelPinButton`, `KebabMenuButton`, `OutboundAddButton`, etc.) — never a new `<button>` with hand-copied or guessed styling.** This is CONTRIBUTING.md's own §0, stated first in that document for the same reason it's stated first here: it's the single most common way a component silently drifts out of spec, since a hand-copied class list renders correctly the day it's written and then quietly stops matching the moment the real `Button` changes, with nothing (`tsc`, a visual diff) ever flagging it. Concrete incident: `CreateNew`'s "New Outbound" trigger hand-copied `Button`'s colors correctly but used `lyra-body-md` (400 weight) for its label instead of `lyra-label` (500 weight, what `buttonVariants` actually applies) — two classes that are both 14px/20px and differ only in weight, so the mismatch shipped and rendered visibly lighter than every other button until caught from a screenshot. If a bespoke control needs behavior none of the existing atoms support, generate its classes from `buttonVariants` (button.tsx) directly — never re-type Button's tokens by hand. Check this before writing or editing any button-shaped element, every time, no exceptions without explicit team approval.

## Component reuse & fidelity

- **"Use Lyra components as designed — never hard-code" (§1, the top rule in the document)** — use the real component's actual behavior, even when a design mockup/screenshot shows something different. Never hard-code a value a real component already computes correctly on its own (a placeholder, a formatted value, a default) just to match a static picture. Hard-coding is only acceptable when the user explicitly asked for that exact value, or when no matching component exists yet and one will be built to replace the placeholder later. Concrete incident: `CreateNew`'s dial-pad field hard-coded `placeholder="Enter phone number"`, silently overriding `PhoneInput`'s own correct per-country example placeholder — the fix was to delete the override, not to make the hard-coded string "smarter."
- "Composition over reimplementation" — before writing any new UI logic (a dropdown, popover, menu, list of clickable items, etc.), check whether `Menu`, `Popover`, or another existing primitive already provides it, and compose that primitive rather than hand-rolling parallel markup. A component that reimplements `role="menu"`/`role="menuitem"` behavior instead of rendering `<Menu>` is a bug, not a style choice — it will drift from the real component every time `Menu` changes.
- "Controlled components," "Z-index hierarchy," "Icons," "File naming & location," "Tailwind & theming," and the "New component checklist" — standing conventions for every component in this repo.
- Whenever creating a form or any form-like set of fields (here or in a consuming app), consult `Input.stories.tsx`'s and `Select.stories.tsx`'s own "Default" playground controls first (Label only, With buttons, Buttons position, Button type, Icon buttons, Button size, Button count, Horizontal, Help, Error, Max width) and compare them against the prototype/design being requested — then compose the field from that matching combination of props, instead of hand-rolling markup for a variant one of these controls already demonstrates.
- **A screenshot of an older or differently-styled interface is still asking for the matching real component, not a from-scratch reproduction of its exact shape.** A different corner radius, size, or color from what a component currently looks like is a prop/className detail to reach for *if that component actually supports it* — not evidence a brand-new one is needed. See PROJECT_SUMMARY.md's "A screenshot of an older/differently-styled interface still means 'use the matching real component'" entry (the `OnlineHelpButton` incident: a filled circular icon button read as "needs a new circular launcher component," when it was just `Button`'s existing "default" variant + an icon size).
- **Reusing the right component doesn't automatically mean the right size was picked for it — check that separately.** The same `OnlineHelpButton` incident went through a fabricated size (`h-12 w-12`, not one of `Button`'s real icon sizes at all) and then a real-but-wrong one (`icon-2xl`, the AppHeader-only tier, picked because it "sounded" like the right tier for a launcher button) before landing on `icon-lg` (36px) — the size that actually matches the other buttons in the same rail. See PROJECT_SUMMARY.md's "Picking a real size token isn't enough" entry, right below the one above: after choosing which component to reuse, separately check its actual neighbors' real rendered size and match that specific one.
- **A className override isn't automatically valid just because a screenshot shows it — check whether the component actually supports varying that property at all.** The same `OnlineHelpButton` incident, a third mistake: it also picked up a `rounded-full` override to match the screenshot's rounder corners, but `buttonVariants` (button.tsx) hardcodes `rounded-lyra-sm` identically across every variant and size — there's no circular/pill option in `Button`'s real API to opt into, so `rounded-full` was a fabricated value, not a legitimate override (same failure as the size guesses above, just applied to shape). See PROJECT_SUMMARY.md's "A component's real shape isn't a free-form override either" entry: before adding any override to a reused component, check the component's own source for whether that property is actually meant to vary — a value hardcoded identically everywhere means no override belongs there.

## Tabs & TabList

- **Every `TabList` gets `overflowMenu` turned on — no exceptions without a real reason.** `overflowMenu` (tabs.tsx) is what makes a row of tabs collapse to "active tab + N More" instead of clipping/wrapping once it runs out of room; it's off by default (so it's an explicit opt-in, not forced everywhere), but that default has repeatedly been mistaken for "responsive collapse is optional" when building a *new* tab bar from scratch. It isn't — every new `TabList` needs it unless that `TabList` has its own different, purpose-built collapse strategy. There is no current exception: `ChannelTab` (`channel-row.tsx`) used to be the one documented case with its own bespoke text-shedding collapse, but that was removed in favor of the same `overflowMenu` pattern every other tab bar uses — see PROJECT_SUMMARY.md's "ChannelTab no longer has its own collapse strategy" entry. Pick `overflowBreakpoint="compact"` over the default `"wide"` specifically when the `TabList` lives somewhere narrow/resizable (a docked or interior panel) rather than a normal page-width tab bar. See PROJECT_SUMMARY.md's "Every TabList needs overflowMenu" entry (Outbound-Campaigns' Monitor dashboard, built without it the first time).
- **Don't patch `TabList` itself to make a layout `className` reach the collapsed row — wrap it in a consumer-owned `<div>` instead, per the existing pattern.** With `overflowMenu` on, `TabList` renders its full row and its collapsed "active + N more" row as two separate siblings inside its own internal wrap div; a `className` passed straight to `TabList` only ever reaches the full row. `lyra-form-generator`'s `FormDetailPage.tsx` already solved this correctly (wraps `TabList` in a plain `<div>` and puts shared layout classes there) — a later attempt to "fix" this at the source in `tabs.tsx` was reverted once it turned out not to actually work and this existing pattern was found. See PROJECT_SUMMARY.md's "TabList + overflowMenu" entry.
- **A tab strip is always fixed to the top of its scrolling container, never part of the scroll itself.** `shrink-0` on the tab row, kept outside whatever wrapper has `overflow-y-auto` — a standing layout rule for any `TabList` sitting above scrollable page/panel content, not something to decide per page. See PROJECT_SUMMARY.md's "Tab strips are pinned to the top of their container" entry.
- **`overflowBreakpoint="wide"`'s full row is horizontally scrollable with chevrons above its own ≤400px threshold — this is built-in, don't re-derive it locally.** If a `"wide"`-mode `TabList`'s tabs don't fit their available width but the row hasn't dropped to ≤400px yet, left/right chevron buttons appear automatically (tabs.tsx); native scroll still works too. Nothing needs to be added in a consuming app for this — it's part of `"wide"` mode itself. (Threshold was originally 991px, lowered to 400px — see the `Tab` max-width/shrink-disabling bullet below for why the old threshold made the chevron state unreachable in practice.) See PROJECT_SUMMARY.md's "TabList's 'wide' mode gained its own scroll-with-chevrons state" entry.
- **`TabList`'s scroll chevrons scroll continuously on hover, not per click — reuse `scroll-chevron.tsx`'s shared `useScrollChevrons`/`ScrollChevronButton` for any new scrollable-with-chevrons UI, don't hand-roll a click-based version.** The same hook/button already power `Select`'s multi-select listbox and `MenuRadix`; `useScrollChevrons` now takes an `orientation: "vertical" | "horizontal"` param (default `"vertical"`) and `ScrollChevronButton`'s `direction` accepts `"left" | "right"` alongside `"up" | "down"`. `TabList`'s own chevrons used to be a separate click-to-scroll-one-tab implementation before this — don't reintroduce that pattern. See PROJECT_SUMMARY.md's "TabList's scroll chevrons switched from click-to-scroll-one-tab to the shared continuous hover-driven affordance" entry.
- **`Tab`'s label truncates + shows a tooltip only when actually truncated — measured, not assumed.** `Tab` always renders its label in a `min-w-0 truncate` span with a `ResizeObserver` comparing `scrollWidth`/`clientWidth`; the wrapping `Tooltip` stays mounted at all times and is toggled via its own `disabled` prop rather than conditionally wrapped/unwrapped — the latter would remount the tab (and its focus/interaction state) every time the truncation state flips. See PROJECT_SUMMARY.md's "Tab truncates its label and shows a tooltip" entry.
- **A `TabList`'s horizontal inset always goes directly on `TabList` itself (`className="px-4"` etc.) — never on a wrapping `<div>`.** `TabList`'s own root element already carries `border-b`; padding sits inside a border in the box model, so an inset placed on `TabList` directly keeps its bottom line full-bleed edge-to-edge while only the tabs move in from the edges — padding on an outer wrapper instead insets the border right along with them. `collapsedRowEl` (the "active tab + N More" row `overflowMenu` swaps in below ≤400px) now also receives this same `className`, so the inset doesn't silently disappear once a strip actually collapses. See PROJECT_SUMMARY.md's "TabList's horizontal inset always goes directly on TabList" entry (the Monitor dashboard's tab strip, inset onto a wrapping div the first time).
- **`Tab` caps at `max-w-[22ch]` and doesn't shrink below that in `overflowMenu overflowBreakpoint="wide"`'s full row — both are load-bearing, not cosmetic.** Without the cap, one unusually long label could dominate a row on its own; without disabling shrink (`[&>[role='tab']]:flex-shrink-0`, tabs.tsx), every tab just kept compressing its own label toward nothing as the row narrowed, so genuine overflow (`scrollWidth > clientWidth`, what actually triggers the chevrons) never occurred until each tab was already crushed to near-zero — a floor so narrow the row always hit the collapse threshold first, making the chevron/scroll state unreachable in practice (this is also why the threshold above was lowered from 991px to 400px). Both overrides back off automatically where a tab is meant to *stretch* instead of size-to-content: `fullWidth` mode and the collapsed row's active-tab slot both reset `max-w-none` (`tabs.tsx`) — don't remove those exemptions if touching this again. See PROJECT_SUMMARY.md's "TabList's 'wide' chevron/scroll state was unreachable for short-label tab sets" entry.

## Layout & responsiveness

- **A `container-type: inline-size` element needs its own explicit width unconditionally, in the component's own base classes — never left for a consumer's `className`/flex-stretch to (maybe) provide.** Caught from a screenshot: `.lyra-tab-overflow-wrap` had no explicit width, so it silently collapsed toward zero (an element with size containment can't use its own content to size itself) even while nested in a flex ancestor that looked like it should stretch it — the chevrons above never appeared, tabs just wrapped their own text instead. See PROJECT_SUMMARY.md's "Follow-up bug, caught from a screenshot" entry — a distinct bug from the `className`-routing one right above it, fixed independently.
- **Card/grid layout responsiveness is always container-query-based, never a Tailwind `sm:`/`md:`/`lg:`/`xl:` viewport prefix.** Check for an existing container-query class first (`.lyra-container-grid`, `.lyra-form-grid`, `.lyra-metric-row`, `.lyra-card-split`) and add a new dedicated one — mirrored in both lyra-tokens.css and storybook.css — if none fits, rather than reaching for a viewport breakpoint as a shortcut. See PROJECT_SUMMARY.md's "Card/grid responsiveness must be container-based" entry (the Monitor dashboard's card grid and summary-card split, both built with viewport prefixes the first time). Note: `.lyra-metric-card-grid` (a fixed-column card-of-cards grid, distinct from `.lyra-metric-row`'s own within-a-single-card responsiveness) was removed as dead code once its one real consumer migrated to `.lyra-container-grid` rows instead — see PROJECT_SUMMARY.md's "Metric Card Grid family removed" entry. Any *external* card grid still just wraps whatever cards it's given; each `DashboardCard`'s own internal `metrics` mode is always independently responsive via `.lyra-metric-row`, regardless of what (if anything) wraps it.
- **Never pair an explicit `height` with a `flex-1`/`flex: 1 1 0%` utility on the same flex item if that item's flex container can ever change `flex-direction` (e.g. via a container-query breakpoint like `.lyra-card-split`'s row → column stack).** `flex-basis` (what `flex-1` sets to `0%`) governs a flex item's size on whatever the *current* main axis is — width in a row, height in a column — so a `flex-basis: 0%` left in place once the container stacks silently overrides any explicit `height` on that same item back toward zero, with no error or warning anywhere. This is exactly what happened to `.lyra-card-split-chart` (a `BarChart` squished to a few visible pixels regardless of what height it was given) until the class was fixed to own its own `flex-grow`/`flex-basis` internally (`flex: 1 1 0%` in the row state, `flex: none` once stacked) instead of a consumer pairing a `flex-1` utility class alongside it. See PROJECT_SUMMARY.md's "the real bug wasn't the height number, it was `flex-basis` fighting `height`" entry.

## Navigation & shell

- **`TreeMenu` supports arbitrary nesting depth — any row (not just top-level) can have its own `children` and expand/collapse itself.** `TreeMenuChild.children`/`defaultOpen` recurse into the same `TreeMenuRow` rendering a top-level `TreeMenuItem` uses (icon-recolor-on-active, chevron, indentation scaling by depth) — don't reach for a second, flat-only tree pattern when a design needs 3+ levels. See PROJECT_SUMMARY.md's "TreeMenu supports arbitrary nesting depth" entry (an "Enterprise" root added above an existing flat category list, which needed to *contain* that list, not sit beside it).
- **`TreeMenu`'s `exactSelection` prop (default `false`) makes selection exact — no parent-active cascade, and any selected row (parent or leaf) gets the same background pill.** Default behavior (cascading parent-active, background pill only on leaves) is still correct for `LeftNav`'s own nav trees, and for `AdminShell`'s default (`navExactSelection` unset/`false`) — only turn this on for a tree meant to have exactly one selected row at a time, at any depth (currently just Outbound-Campaigns' Monitor dashboard, via `AdminShell`'s `navExactSelection` prop). See PROJECT_SUMMARY.md's "TreeMenu gains exactSelection" entry.
- **Every new page in a consuming app renders `AdminShell` — a hand-rolled root layout (own `SidePanel`, own `PageHeader`, own pin/hover/narrow-container-guard state) is not an acceptable alternative, even when `AdminShell` doesn't yet support something the new page needs.** Extend `AdminShellProps` instead — that's exactly how `navHeaderBadge` (a view-switcher badge next to the nav title), `navExactSelection` (forwarded to the internal `TreeMenu`), `navKey` (forces that `TreeMenu` to remount when `navItems` swaps to a different dataset), and `pageSubtitle` (forwarded to `PageHeader`'s `subtitle`) came to exist — all optional, all off/undefined by default, so no existing `AdminShell` consumer is affected. Concrete incident: Outbound-Campaigns' Monitor dashboard was originally built with its own root `<div>` instead of `AdminShell`, which is why it never got `AdminShell`'s baked-in `animate-in fade-in-0 duration-500` entrance (missing entirely, while Configure's `AdminShell`-based page had it) and needed its own from-scratch copy of the container-width pin guard `AdminShell` already provides. See PROJECT_SUMMARY.md's "AdminShell gains navHeaderBadge/navExactSelection/navKey/pageSubtitle" entry.

## Dashboards, filters & charts

- **`DashboardTemplate` (dashboard-template.tsx), not `AgentDashboard`, is the reusable dashboard shell — reach for it when building any new dashboard-style page.** It owns only the container/width/breakpoint mechanics (`maxWidth`-capped, centered column + the `lyra-container-grid-wrap` container-query boundary) and takes arbitrary `children` — compose it with whatever card grid class fits the page (`.lyra-container-grid`, `.lyra-card-split`, or plain `DashboardCard`s). `maxWidth` accepts `number | string` — a bare number means px, a string is used as-is; pass `maxWidth="none"` for a full-width dashboard, **never** `className="max-w-none"` — the cap is an inline `style`, which always wins over any class regardless of `cn`/`twMerge` order. `AgentDashboard` is a specific, fully-baked persona composition (one agent's greeting, queue widgets, Contact History + Redial, Performance/Productivity) built *on* `DashboardTemplate` — it's a real, still-supported template for that exact use case, but not the generic one; don't gut it down to its wrapper div as a substitute for using `DashboardTemplate` directly. See PROJECT_SUMMARY.md's "`AgentDashboard` shouldn't be the template" entry, and the Storybook stories: `Templates/Dashboards` (generic shell — "Dashboards" + "Full Width" variants) vs. `UI/Agent Dashboard` (the persona-specific one).
- **A single-select date range (or any "only one choice applies" filter) is `DateRangeFilterChip` (date-range-filter-chip.tsx), not `FilterChip`'s default checkbox multiselect.** Extracted out of `AgentDashboard`, which used to define this "Date: {label}" `RadioGroup`-popover trigger locally (as an unexported `DateFilterChip`) and duplicate it three times in one file — now a real, standalone, exported component (`value`/`onValueChange` optionally controlled, `options`/`label` overridable) any consumer can reach for. `AgentDashboardDateRange` stays exported as a type alias for backward compat. See PROJECT_SUMMARY.md's "Outbound-Campaigns' Monitor cards reuse AgentDashboard's date filter" entry (the incident: Monitor's cards had a checkbox-multiselect `FilterChip` for a single-choice value, the wrong control from the start).
- **`DateRangeFilterValue` is intentionally wider than any one consumer's own option set — always narrow with `Exclude<DateRangeFilterValue, ...>` for a local type used in a `Record<>` lookup or a `useState`, never re-alias the full type directly.** `DateRangeFilterValue` grows as new consumers need new values (`"last30"`/`"last90"` were added for Outbound-Campaigns' Monitor page's 5-option toolbar filter) — a consumer that only ever offers a subset of options (e.g. `AgentDashboard`'s default 4: Today/Yesterday/Last 7 days/Custom) must exclude what it doesn't use in its own type alias (`AgentDashboardDateRange = Exclude<DateRangeFilterValue, "last30" | "last90">`), or every `Record<..., X>` lookup keyed on it breaks the moment the shared type grows again. A `DateRangeFilterChip` consumer that only passes `onValueChange` (not a narrower `options` type) may also need a cast at the call site (`(v) => setState(v as MyNarrowerType)`) since the prop's own callback type is always the full `DateRangeFilterValue` — safe as long as that consumer's own `options` list never actually offers the excluded values. See PROJECT_SUMMARY.md's "Monitor's per-card date filters consolidated into one toolbar-level filter" entry (the incident: widening the type for Monitor broke 4 of `AgentDashboard`'s own exhaustive lookups).
- **A "click a card, open its InteriorPanel" pattern always shows the triggering card as selected while its panel is open — reuse `DashboardQueue`'s existing `variant="info-strong"`/`"neutral-subtle"` toggle, don't invent a new selected-state mechanism on `DashboardCard`.** No new prop was needed: `variant` is already plain `ContainerProps` passthrough, so a consumer just conditions it on whatever tracks which panel is open (`isSelected`/`interiorPanelTitle === card.title`, etc.), plus `aria-pressed` on the same condition. Both `Templates/Dashboards` (Dashboards.stories.tsx, the reference demo) and Outbound-Campaigns' Monitor page do this now — any future consumer of this click-to-open-panel pattern should too. See PROJECT_SUMMARY.md's "the triggering card shows a selected state while its panel is open" entry.
- **The chart library covers Line, Scatter (+ Bubble), Heatmap, Gauge, Funnel, Treemap, Sunburst, and Box Plot, alongside Bar (+ Stacked) and Donut (+ center label) — check this list before assuming a chart type needs to be built from scratch.** All follow `bar-chart.tsx`'s architecture (the shared `Chart` ECharts wrapper, `resolveCssColor`/`useThemeVersion` for every color, axis-bearing ones resolving axis/legend text the same way). Two shared color-cycling helpers live in `chart.tsx` for "no per-item color supplied" cases: `getDefaultAccentColorVar` (flat cycle, `FunnelChart`'s default) and `getDefaultAccentHue` (soft/strong pairs — a `TreemapChart`/`SunburstChart` parent gets a hue's `-strong` stop, its uncolored children get that hue's `-soft` stop). Both still defer to an explicit per-item `colorVar` when a consumer has real meaning to encode — reach for a real `colorVar` (including the semantic-status-color exception below) before relying on either cycle. See PROJECT_SUMMARY.md's "Chart library expanded" entry for the full per-component breakdown, plus which catalog items were deliberately left out (violin, progress/bullet — no native ECharts series for either) and why.
- **A chart's axis labels, axis lines/grid lines, and legend text need the same canvas-color-resolution treatment as series colors — `resolveCssColor`/`useThemeVersion` (chart.tsx), never a bare `var(--lyra-color-...)` string handed straight to ECharts' `axisLabel`/`axisLine`/`splitLine`/legend `textStyle`.** `<canvas>` can't resolve a CSS custom property; an unresolved one silently falls back to ECharts' own hardcoded gray, which then never changes when `[data-theme]` flips. `bar-chart.tsx` uses `--lyra-color-fg-secondary` for label/legend text and `--lyra-color-border-subtle` for axis/split lines — the standard tokens for muted text and light separators respectively. Follow this for any new axis-labeled or legend-bearing chart; `DonutChart`/`Sparkline` don't need it since neither has axes/legend of its own. See PROJECT_SUMMARY.md's "`BarChart`'s axis/legend text now resolves real lyra tokens" entry.
- **Never use primary/brand, or a raw light/dark literal, for a dashboard icon or a chart series — icons in dashboards get a subtle treatment, chart series get the accent (data-visualization) palette.** Concretely: a dashboard `headerIcon` (`Icon`'s `background` prop) should never be `"primary"` (the solid brand-blue fill, `bg-lyra-bg-primary`) — reach for the already-subtle options instead (`"active"`, `"info"`, `"success"`, `"warning"`, `"critical"`, `"neutral"`, `"surface"`, `"shell"` — all a light/subtle background with a colored icon, never a solid saturated fill). A chart series' `colorVar` (`BarChart`/`DonutChart`) should be one of the `--lyra-color-accent-{slate,red,orange,yellow,lime,green,teal,purple,pink}-strong` tokens (lyra-tokens.css) — **never `accent-blue-strong`** (too easily read as the primary/brand color, not a neutral category) and never a `status-*`/`bg-primary`/`fg-*` token as a stand-in for "just needs some color." **Exception**: if a chart's colors map onto a specific semantic element that already has its own color (status/success/warning/critical, e.g. `DonutChart`'s Available/Working/Unavailable activity breakdown), using that element's real status color is correct — the rule is about arbitrary/categorical series with no inherent meaning (e.g. "Emails Launched" vs. "Emails Remaining"), not every chart unconditionally. See PROJECT_SUMMARY.md's "chart series colors must be accent (data-viz) colors, not status colors" entry — the incident this rule was written to prevent: the Email `BarChart`'s two series shipped with `status-info-strong`/`fg-secondary`, neither an accent color nor tied to any real status.
- **Any control meant to live inside a `DashboardCard`'s `headerActions` (or any other slot inside a card that might itself become clickable) must call `e.stopPropagation()` on its own trigger.** `KebabMenuButton` already did this; `DateRangeFilterChip`'s trigger button didn't, and the gap only surfaced once Outbound-Campaigns' Monitor page made its `DashboardCard`s themselves clickable (opening a right `InteriorPanel`) — clicking the date popover was also bubbling up and firing the card's own `onClick`. Fixed at the source in `date-range-filter-chip.tsx`, not patched around in the consumer. Check this for any *new* header-slot control, not just these two. See PROJECT_SUMMARY.md's "Outbound-Campaigns' Monitor cards click (or kebab 'Edit') to open a right InteriorPanel" entry.

## Panels, menus & overlays

- **Wiring up ANY `Draggable`-backed floating panel (`AiPanel`, `DraggablePanel`, or `Draggable` directly) in a consumer app — a recurring bug, now a checklist, check this BEFORE writing any panel wiring in a new or existing repo:**
  1. **Never attach `onMouseDown` to an app-level ancestor `<div>` wrapped around the panel** (e.g. a `pointerEvents:"auto"` div inside the outer `position:fixed; pointerEvents:"none"` positioning wrapper) to detect clicks for z-index "bring to front" ordering. Use the panel's own **`onInteract` prop** instead (`AiPanel`/`DraggablePanel` both forward it straight onto `Draggable`'s real root node — see `draggable.tsx`'s `onInteract` doc comment). Reason: the drag gesture moves the panel via CSS `transform`, which does **not** move an ancestor's layout box — so an ancestor wrapper with `onMouseDown`/`pointer-events:auto` gets left behind as an invisible "ghost" hit area at the panel's *original* (pre-drag) position once the user drags it elsewhere, silently swallowing clicks meant for whatever real UI (often a page header's own buttons) happens to sit there instead. `Draggable`'s own root already sets `pointer-events:auto` on itself and correctly moves with the transform — no ancestor override is needed for hit-testing at all.
  2. **The outer float-positioning wrapper (`position:fixed`, `pointerEvents:"none"`) needs no inner `pointerEvents:"auto"` div either** — remove it, don't just leave it inert. Render the panel directly as that wrapper's child. The wrapper's only job is holding the fade/slide open-close animation styles (`opacity`/`transform`/`visibility`/`transition`) and the fixed `top`/`left`/`zIndex`.
  3. **Multi-panel z-index ordering** (when more than one panel can float at once): a single `topPanel` state (`"panelA" | "panelB" | ... | null`) in the parent, each panel's wrapper reading `zIndex: topPanel === key ? 10000 : 9999`, and each panel's `onInteract` calling `setTopPanel(key)` — no other mechanism. This is `draggable.tsx`'s own documented "Multi-Panel Z-Index & Docking Rules" contract.
  4. This exact bug (rule 1 violated) has now recurred at least three times across separate consumer repos before being caught each time — `lyra-ux-templates`, `lyra-form-generator`, and Outbound-Campaigns' `App.tsx` (repro pattern: open a panel → undock it → drag it away from its start position → nearby unrelated UI, especially a page header's buttons, stops responding to clicks). `AdminShell.stories.tsx`'s `AdminShellWithAiDemo` — the single most-copied reference for this pattern — still had the milder sibling anti-pattern (the inert-but-still-present inner `pointerEvents:"auto"` div from rule 2) until it was cleaned up alongside this rule being written; `AgentNextGenPage.tsx` (agent-next-gen-v1) and `AgentNextGenTemplate.stories.tsx` were already correct and are the right multi-panel reference to copy from. Check any file being used as a copy-from reference for this rule before trusting it.
- **Any scrollable dropdown list in this library uses the shared hover-chevron affordance (`scroll-chevron.tsx`'s `useScrollChevrons`/`ScrollChevronButton`) instead of a native OS scrollbar — never let a consumer's `overflow-y-auto`/`max-h-*` className create a plain scrollbar by accident.** `Select`'s multi-select listbox and `MenuRadix` already did this; the hand-rolled `Menu` (menu.tsx) now does too — its root split into an outer surface wrapper (border/shadow/rounded/`p-1`, whatever a consumer's `className` controls) and an inner `flex-1 min-h-0 overflow-y-auto lyra-scrollbar-hide` scrollable div (the actual items), with chevrons as pinned siblings above/below it, matching `MenuRadix`'s own `Content` structure exactly. A `Menu` consumer that needs to cap height should pass its `max-h-*` in `className` as before — do NOT also add `overflow-y-auto` to that className; `Menu` owns the actual scrolling internally now. See PROJECT_SUMMARY.md's "`Menu` gains the shared hover-chevron scroll affordance" entry (the incident: `Autocomplete`'s and `PhoneInput`'s country/option dropdowns both showed a plain scrollbar, caught from a screenshot).

## Fields & text

- **Every text-entry/select-style component supports `size?: "sm" | "md"` (default `"md"`, 36px/`h-9`) — `"sm"` is 32px/`h-8`, for dense contexts like a table toolbar.** `Input`, `SearchInput`, `Select`, `EmailInput`, `PasswordInput`, `PhoneInput`, `NumberField`, `Autocomplete`, `DatePicker`/`DateRangePicker`, `TimePicker`/`TimeRangePicker`, and `DateTimePicker`/`DateRangeTimePicker` all have it now — reach for `size="sm"` instead of a one-off `h-8`/`scale` override, and give any *new* text-field-style component the same prop from the start rather than inventing a different sizing scheme. Only the field's own height changes — padding, icon size/position, and any popover/dropdown content (a `Select`'s listbox, an `Autocomplete`'s rows, a `DatePicker`'s calendar, `PhoneInput`'s country panel) stay full-size regardless of trigger size, same as a compact button doesn't imply a compact menu. Where a props interface extends `React.InputHTMLAttributes<HTMLInputElement>`, `"size"` must be added to the existing `Omit<...>` list — the native HTML `size` attribute is a `number` (character width) and will conflict with this string-union prop otherwise. See PROJECT_SUMMARY.md's "Every text-entry/select-style component gained a `size` prop" entry.
- **Labels and header text default to Title Case (every word capitalized — "Wait Time", "Outbound Email"), not sentence case.** Only body copy and tooltip copy are sentence case. See PROJECT_SUMMARY.md's "Text capitalization" entry under Important Patterns — its wording used to say "first-letter capitalized," which reads backwards (like "capitalize only the first letter") and caused a real misapplied fix in Outbound-Campaigns' Monitor dashboard; say "Title Case" instead of "first-letter capitalized" anywhere this comes up.

## Process & verification

- **After editing a multi-line `/* ... */` doc comment in this repo, re-read the whole comment, not just your own diff — `tsc --noEmit` is not sufficient to catch a premature closing `*/`.** This exact mistake (a new paragraph accidentally closes the block early, leaving the original comment's remaining text as bare unparseable code) has happened twice — once in `agent-dashboard.tsx` (`tsc` caught it, 19 cascading errors) and once in `Dashboards.stories.tsx` (`tsc` reported clean; the user only found out live via Storybook's "Failed to fetch dynamically imported module" error). After any doc-comment edit, verify with a direct `esbuild` bundle of the touched file (`platform: "browser"`, `jsx: "automatic"`, `external` for `react`/`react-dom`/`lucide-react`/`@storybook/*`) in addition to `tsc --noEmit` — that's the same bundler Storybook's Vite dev server actually uses, and it will catch what `tsc` sometimes doesn't.

## Repo history & scope rules

`PROJECT_SUMMARY.md` is the repo's history log — at ~650KB it does NOT fit in a context window, so do not try to read it in full. Instead, before making changes in this repo (or any sibling repo that has this one mounted alongside it):
- **Grep its `###` entry headings for every component/file you're about to touch** (e.g. `grep -n '^###.*TabList' PROJECT_SUMMARY.md`) and read the matching entries. **Read ALL matches, not just the first — later entries supersede or revert earlier ones**; the newest matching entry is the current truth.
- Read its "How to read this file" preamble once per session — it explains the sections and the entry conventions.
- **When you finish a notable change, append an entry** (`### <Title naming the component/file>` under the right section) following the entry template in the preamble: dated, ≤15 lines, and if it supersedes an earlier entry, say which one by title.

In particular:
- "Important Patterns" and "Scope Rules" — standing conventions for this repo itself (e.g. new Tailwind colors/CSS variables must be added to both their light-DOM file and their Storybook-fallback file; don't reach for a raw Tailwind value without checking existing components/tokens first).
